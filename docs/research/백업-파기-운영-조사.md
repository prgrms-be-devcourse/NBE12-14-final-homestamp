# 백업 보존·파기 운영 조사

조사일: 2026-11-17. 범위: 공개된 AWS 공식 문서, 개인정보보호위원회의 공개 처리방침, 서비스 제공자의 공개 보존 안내. 아래는 출처의 설명과 운영 검토 사항이며 한국 법률의 해석이나 적법성 결론이 아니다.

## 공식 자료에서 확인한 내용

- 개인정보보호위원회 개인정보 포털의 **개인정보의 파기 절차 및 파기방법**은 보유기간 경과 또는 처리목적 달성으로 불필요해진 정보의 지체 없는 파기와 다른 법령에 따른 보존 예외를 설명한다. 이는 해당 기관의 처리방침이며, 백업에서 특정 개인의 삭제를 언제 어떻게 완료해야 하는지에 대한 별도 해석은 확인하지 못했다. [개인정보 포털 개인정보처리방침](https://www.privacy.go.kr/front/contents/cntntsView.do?contsNo=149)
- RDS DB 인스턴스 자동 백업 보존기간은 0~35일로 설정하며, 인스턴스 정지 시간은 계산에 포함되지 않아 설정 기간보다 오래 보존될 수 있다. Multi-AZ DB 클러스터의 해당 문서상 범위는 1~35일이다. 따라서 설정값만으로 실제 백업의 최장 존속기간을 단정할 수 없다. [RDS Backup retention period](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.BackupRetention.html)
- DB 인스턴스를 삭제해도 수동 스냅샷은 남으며, 다른 리전에 복제된 자동 백업도 자동 백업 보존을 선택하지 않았을 때 남을 수 있다. 최종 스냅샷은 자동 백업과 별개이고 자동 만료되지 않는다. [RDS Deleting a DB instance](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_DeleteInstance.html), [Retaining automated backups](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.Retaining.html)
- AWS Backup의 Vault Lock이 활성화된 보관소에서는 복구 지점 삭제·수명주기 변경이 거부된다. Compliance 모드의 유예기간이 지나면 잠금 설정을 변경하거나 제거할 수 없다. 기존 복구 지점은 잠금의 최소·최대 보존 설정이 아니라 기존 수명주기를 따른다. [AWS Backup Vault Lock](https://docs.aws.amazon.com/aws-backup/latest/devguide/vault-lock.html)
- AWS Backup의 삭제 작업은 권한 문제 등으로 실패할 수 있으며, 만료 상태의 복구 지점이 계정에 남을 수 있다. 백업 계획 변경은 이미 생성된 복구 지점에 적용되지 않는다. [AWS Backup deletion](https://docs.aws.amazon.com/aws-backup/latest/devguide/deleting-backups.html)
- Google은 재해 복구용 암호화 백업에 데이터가 최대 6개월 남을 수 있고, 장애나 프로토콜 실패 등으로 처리 시간이 지연될 수 있다고 설명한다. 이는 Google의 서비스 정책 사례이며 HomeStamp의 적정 기간이나 법적 허용기간을 의미하지 않는다. [How Google retains data we collect](https://policies.google.com/technologies/retention)
- OpenAI는 Enterprise의 비활성 Library 파일이 내부 백업에 추가로 최대 30일 남을 수 있고 보안·법적 의무에 따른 더 긴 보존이 가능하다고 설명한다. 이는 특정 서비스·파일에 한정된 사례다. [Chat and file retention in ChatGPT, Enterprise compliance considerations](https://help.openai.com/en/articles/8983778-chat-and-file-retention-in-chatgpt)

## 운영 설계에서 확인할 사항

1. 실제 사용 중인 DB, 자동 백업, 수동·최종 스냅샷, 별도 백업과 리전·계정 간 복제본을 목록화하고 각각의 보존 설정과 삭제 담당자를 확인한다.
2. 운영 DB 삭제 시각과 백업의 실제 삭제 완료 시각을 구분하고, 복원 시 이미 삭제한 개인정보가 다시 활성화되지 않도록 삭제 이력 재적용과 검증 절차를 설계한다. 이는 위 자료에서 도출한 운영상 검토 제안이며, 구현 여부는 확인하지 않았다.
3. 잠금, 삭제 권한, 삭제 실패 알림, 예외 보존 및 정기적인 복원·만료 확인을 함께 점검한다. AWS의 만료 표시는 삭제 성공의 증거로 가정하지 않는다.
4. 고정 기간을 외부 사례에서 가져오기 전에 실제 구성의 최대 잔존기간과 예외, 안내 문구, 적용 법령에 대해 담당자 및 필요 시 법률 전문가의 검토를 받는다.

## 확인되지 않은 점

이 조사는 현재 HomeStamp의 실제 AWS 구성, 백업 복제·잠금 여부, 운영 DB 삭제 구현, 백업 복원 절차 또는 계약상 의무를 확인하지 않았다. 개인정보보호위원회 자료에서 백업 사본의 개인별 삭제 유예를 일반적으로 허용하는 명시적 근거는 찾지 못했다. 위 사례나 AWS 기능만으로 특정 보존기간의 적법성을 판단할 수 없다.

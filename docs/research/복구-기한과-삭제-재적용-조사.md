# 복구 기한과 삭제 재적용 조사

조사일: 2026-11-17. 범위는 RDS DB 인스턴스의 시점 복구, 장애 후 삭제 재적용과 그 검증이다. AWS 공식 문서 및 저장소의 해당 절만 읽었으며 실제 AWS 설정·운영 데이터·복구 실행 결과는 확인하지 않았다. 아래는 조사 결과이며 새로운 운영 기준의 확정이나 구현 완료를 뜻하지 않는다.

## 확인된 사실

- RDS DB 인스턴스의 자동 백업 보존 설정은 0~35일이며 0이면 자동 백업이 꺼진다. 중지 상태의 시간은 보존 기간 계산에서 빠지고 중지 중 자동 백업은 생기지 않아, 설정 일수와 실제 사본의 경과 시간은 같지 않을 수 있다. 0과 양수 사이를 변경하면 중단이 발생한다. [AWS RDS 백업 보존 기간](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.BackupRetention.html)
- RDS는 DB 인스턴스의 트랜잭션 로그를 5분마다 S3에 업로드한다. 실제 복구 가능 최신 시각은 `LatestRestorableTime`으로 확인하고, 보존 범위 안의 시각으로 복구하면 원본을 고치지 않고 새 인스턴스가 만들어진다. 따라서 5분 주기는 5분 손실 상한이나 서비스 RPO 보장이 아니다. 복구 후에도 데이터 블록 초기화가 진행되어 성능이 낮을 수 있고 보안 그룹·파라미터 그룹 등 복구 설정을 확인해야 한다. [AWS RDS 시점 복구](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)
- RPO는 허용 가능한 데이터 손실 시점, RTO는 장애에서 서비스를 복구하기까지 허용하는 시간 목표다. 목표값은 팀이 정하고 실제로 측정해야 한다. [AWS 재해 복구 목표](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/disaster-recovery-dr-architecture.html)
- DB 변경과 아웃박스 삽입을 같은 트랜잭션에 두면 둘 중 하나의 실패 시 함께 롤백한다. 외부 전송은 별도이므로 중복 처리에 대비해 소비자의 멱등성과 필요한 순서를 설계해야 한다. 이 패턴만으로 외부 저장 완료나 장애 시 유실 없는 복구가 보장되지는 않는다. [AWS 트랜잭셔널 아웃박스](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

## 저장소에서 확인한 계약과 공백

- `docs/rules/06-요구사항-명세.md` 설정값 표는 탈퇴 후 대상 기록 파기를 달력 기준 5일 이내로 정하고, NFR-REL-3은 자동 백업의 실제 보관·복구 가능 범위 확인을 요구한다. 같은 문서 「탈퇴 파기 운영 검토안」은 장애 후 미처리 확인·재시도를 제안하되 담당·감시·주기 등을 미확정으로 둔다. 5일 파기 기한은 RPO나 RTO가 아니다.
- `docs/rules/04-인프라-아키텍처.md` 4장 DB·백업 표는 단일 AZ, 자동 백업 보존 5일 검토, 복구 시각 T 이후 삭제 및 수신 거부 재적용을 기술한다. 13장 장애 표는 DB 장애 시 서비스가 멈춘다고 명시한다. 로컬 가짜 데이터 연습 계획은 실제 RDS 복구 시간 측정 결과가 아니다.
- `docs/runbooks/DB-보관-삭제.md` 「호출 트랜잭션」은 삭제 감사와 `S3_DELETE`·`AUDIT_WRITE` 아웃박스를 삭제와 함께 커밋하고 이후 작업자가 외부 작업을 재시도하도록 한다. 함수 자체는 아웃박스 생성과 삭제 기한을 검사하지 않는다.
- 최신 `origin/dev`의 `back/src/main/resources/db/migration/V1__init_schema.sql`에서 `deletion_log`, `outbox`, 감사 대조 후 호실을 삭제하는 함수를 확인했다. 저장소에 병합된 코드가 실제 운영에 배포되었다는 뜻은 아니다. `docs/rules/05-ERD-초안.md` 2-9의 삭제 기록은 행동 식별자·호실·순번·해시 등을 보존하지만 모든 삭제 종류를 복구 후 재실행하는 완전한 명령 목록이나 외부 보관 완료를 보증하는 절차는 여기서 확인되지 않았다.
- **추론:** T 이후 DB 삭제가 커밋됐으나 `AUDIT_WRITE`가 외부 저장되기 전에 DB가 손실되고 T로 복구하면, 복구 DB의 아웃박스와 S3 감사 모두 그 삭제를 놓칠 수 있다. 반대로 이미 S3가 처리한 작업이 복구 DB에서 다시 대기할 수도 있다. 외부 감사만 읽어 T 이후 삭제 전부를 찾을 수 있다고 가정하면 안 된다. S3 감사 기록에 호실 삭제, 사진 지움, 탈퇴, 수신 거부 변경 등 각 유형의 재적용에 필요한 식별자·순서·완료 상태가 충분한지와 민감정보 최소화도 별도 검증이 필요하다.
- 특히 수신 거부의 추가와 해제는 순서와 인증 조건을 지켜야 하며, 단순히 모든 과거 행을 다시 추가하는 방식은 현재 상태를 잘못 만들 수 있다. `docs/rules/05-ERD-초안.md` 2-1 `sms_opt_out`, 2-9 `deletion_log` 참조.

## 아직 정해지거나 입증되지 않은 것

실제 백업 설정과 최신·최초 복구 가능 시각, 허용 손실량(RPO), 장애 감지부터 사용자 요청 정상 처리까지의 RTO, 담당자·대리·연락과 장애 중 기한 초과 대응은 확인되지 않았다. 수동·최종 스냅숏과 사본의 목록·보존 기한도 별도 확인이 필요하다. 삭제 사실을 복구 시점과 무관하게 빠짐없이 찾을 권위 있는 대장, 대장과 DB의 원자성 또는 누락 감지·조정 방법, 재적용 스크립트와 권한·완료 기준은 확정되거나 검증된 것으로 볼 수 없다. 삭제 대장을 외부에 둔다고만 정해서는 DB와 대장 사이의 이중 쓰기 문제가 사라지지 않는다.

## 검증 제안

1. 팀이 장애 종류별 RPO·RTO와 5일 파기 기한의 담당·알림·초과 대응을 정한다. 복구 완료는 인스턴스 생성뿐 아니라 격리, 삭제·수신 거부 재적용, 건수와 표본 검증, 연결 전환, 정상 요청 확인까지 포함해 정의한다.
2. 가짜 데이터와 격리된 테스트 S3 경로로 복구 시각 전후에 호실 삭제, 사진 삭제, 탈퇴, 수신 거부 추가·해제를 만들고, 커밋 전후·외부 쓰기 전후·작업 완료 표시 전후 장애를 주입한다. 외부 대장 누락, 중복·순서 역전, 부분 성공, 재시작을 확인한다.
3. 같은 재적용을 두 번 실행해 결과가 바뀌지 않는지, T 이후 삭제된 데이터가 다시 노출되지 않는지, 각 유형의 예상 건수와 감사 기록이 일치하는지 검증한다. 누락이나 불일치가 있으면 서비스 공개를 중단하고 담당자가 조사하는 절차를 정한다.
4. 별도의 격리된 RDS 복구 연습에서 실제 `LatestRestorableTime`과 선택한 T, 장애 감지·복구 요청·사용 가능·재적용·검증·전환 시각을 기록한다. 관찰 손실과 전체 경과 시간을 목표와 비교하고, 백그라운드 초기화 중 성능과 보안·연결 설정도 확인한다. 실제 운영 데이터와 운영 경로를 연습에 사용하지 않는다.

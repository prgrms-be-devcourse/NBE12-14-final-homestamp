# 이미지 발행(GHCR) 런북 (백엔드·화면)

`back/` 이미지를 빌드하고 보안 검사를 통과한 것만 GHCR에 올려, 배포에 쓸 **digest**를 내는 절차다. 설정 원본은 `.github/workflows/image-publish.yml`과 `.github/scripts/image/`. 운영 배포는 하지 않는다(digest를 받아 `deploy.yml`이 따로, 승인 뒤).

- **지금은 발행이 꺼져 있다.** 저장소 변수 `IMAGE_PUBLISH_ENABLED`·`IMAGE_REPOSITORY`가 없어서 main에서도 빌드·검사만 하고 Push하지 않는다
- 아직 GHCR에 올린 적이 없다. 로컬 시험(시험용 레지스트리)과 PR CI의 빌드·검사만 했다

```
PR(back/ 바뀜)     빌드(linux/amd64) → Trivy → 결과 보관                         (packages 권한 없음)
main push·수동     백엔드 검증(spotless·테스트) → 빌드 → Trivy → [발행 허용?]
                     └ 허용: 이미지 넘김 → 같은 이미지인지(ID) → GHCR 로그인(GITHUB_TOKEN)
                             → sha-<커밋> 태그로 Push → 레지스트리 digest 확인 → 요약에 digest
                     └ 아님: 여기서 끝(이유를 출력)
```

## 발행과 digest

- 태그는 `sha-<커밋 40자>` 하나(`latest` 없음). **이미 있으면 덮어쓰지 않는다**: 같은 커밋 라벨·linux/amd64면 그 digest를 돌려주고(재실행), 아니면 실패
- digest는 **레지스트리에 실제로 있는 manifest 원문의 SHA-256**이다. 그리고 이 로컬 이미지가 올라간 digest(RepoDigests)와 같아야 한다(올린 직후 누가 태그를 바꾸면 실패)
- 그 digest로 다시 받아 `linux/amd64`와 커밋 라벨(`org.opencontainers.image.revision`)을 확인한다
- 목록(index)으로 올라가면(Docker 설정에 따라) `linux/amd64`와 빌드 증명용 `unknown/unknown` 말고 다른 플랫폼이 있으면 실패. 배포는 그 목록의 digest를 그대로 쓴다(`deploy.sh`·`deploy.yml` 모두 목록과 단일 이미지를 받는다)
- 검사한 이미지와 올린 이미지가 같은지: 빌드 job의 이미지 ID를 발행 job이 받은 이미지와 비교

| 종료 | 뜻 |
|---|---|
| 20 | linux/amd64가 아님 |
| 21 | 커밋 라벨이 이 커밋이 아님 |
| 22 | 태그가 다른 이미지를 가리킴(덮어쓰지 않음) |
| 23 | 레지스트리 조회 실패(인증·네트워크) |
| 24 | Push 실패 |
| 25 | digest 확인 실패(태그가 바뀜, 다른 플랫폼, 형식) |

GitHub Actions가 성공했다고 패키지가 공개라는 뜻은 아니다. 공개 여부는 패키지 설정에서 따로 확인한다.

## 공개 전 조건과 절차 (아직 하지 않음)

**저장소가 공개라 첫 Push가 공개 패키지가 될 수도 있고**(GitHub 문서끼리 다르다: 컨테이너 문서는 "처음에는 비공개", Actions 문서는 "저장소의 공개 여부를 따른다"), **한 번 공개하면 비공개로 되돌릴 수 없다.** 그래서 첫 발행 전에 아래를 모두 끝낸다.

1. 팀 승인: 이미지 이름, 공개(04 9-3), 승인한 사람을 decisions에 남긴다
2. #173(됨)·#299·이 PR(RDS 인증서)이 `main`에 들어감(위 "일회성 실행이 모두 들어가기 전 이미지는 발행하지 않는다")
3. 공개 전 검토: 그 커밋의 PR CI artifact(Trivy) 통과, 이미지 안 파일 목록(`/app/app.jar`와 `/app/certs/rds-ca.crt`만 앱 파일, 인증서 SHA-256이 04 6장과 같음), jar 안 `application.yml`에 운영 값이 없음(local·test 고정 키만, 04 6장)
4. 조직 설정: 조직 Owner에게 Packages → Package creation에서 공개 패키지 생성이 허용되는지 확인(막혀 있으면 첫 Push 뒤 공개로 바꿀 수 없다)
5. 저장소 Admin: 변수 `IMAGE_REPOSITORY=ghcr.io/prgrms-be-devcourse/homestamp-back`(승인한 이름), `IMAGE_PUBLISH_ENABLED=true`
6. Actions → image-publish → Run workflow(main) → 요약의 digest 확인
7. 패키지 설정에서 저장소 연결과 공개 여부 확인. 비공개로 생겼으면 승인대로 공개로 바꾼다(되돌릴 수 없음)
8. 익명 Pull 확인: 로그인하지 않은 곳에서 `docker pull ghcr.io/…/homestamp-back@<digest>`. 공개 패키지는 개인 AWS 계정의 EC2에서도 인증 없이 받는다(GitHub 문서)

발행을 멈추려면 `IMAGE_PUBLISH_ENABLED`를 지운다(이미 올린 이미지는 남는다).

## 화면 이미지 (`front/Dockerfile`, `front-image-publish.yml`)

화면(React)은 백엔드와 **따로** 빌드·검사·발행한다(2026-11-27 B안). 이미지는 정적 파일 운반용이고 **실행하는 컨테이너가 아니다**. 배포(front-deploy, 후속)가 `docker create` → `docker cp`로 `/site`만 꺼내 nginx가 내는 `/srv/homestamp/front/releases/<커밋>`에 푼다.

```
PR(front/ 바뀜)    의존성 검사 → 빌드(linux/amd64) → 내용 확인 → 이미지 비밀값 검사 → 결과 보관   (packages 권한 없음)
main push·수동     화면 검증(lint·format) → 위와 같음 → [화면 발행 허용?] → 같은 이미지인지(ID) → sha-<커밋> Push → digest
```

| 항목 | 값 |
|---|---|
| 워크플로 | `front-image-publish.yml`. 트리거 `front/**`·자기 파일·`.github/scripts/image/**`. 백엔드 `image-publish.yml`(`back/**`)은 그대로라 화면만 바뀌면 백엔드 빌드는 돌지 않고, 공통 스크립트가 바뀌면 둘 다 돈다 |
| 발행 허용 | main + push/수동 + 저장소 변수 **`FRONT_IMAGE_PUBLISH_ENABLED=true`** + **`FRONT_IMAGE_REPOSITORY`**(`gate.sh` 같은 규칙). 백엔드 변수와 따로 켠다. **지금은 꺼져 있다**(변수 없음) |
| 이름 | 추천 `ghcr.io/prgrms-be-devcourse/homestamp-front`. 백엔드와 같은 확인(공개 승인·같은 이름 비공개 패키지 없음) 뒤 변수로 정한다 |
| 발행 | 백엔드와 같은 `publish.sh`: 태그 `sha-<커밋>` 하나, 덮어쓰지 않음, linux/amd64·커밋 라벨 확인, 레지스트리 digest 확인. 검사한 이미지 ID와 올리는 이미지 ID가 같아야 함 |
| 빌드 | `node:22.23.5-bookworm-slim`(digest 고정, CI `front` job과 같은 Node 22) → `npm ci` → `npm run build`(`tsc -b && vite build`). 빌드 단계는 빌드하는 기계 플랫폼에서 돌고 결과 이미지만 linux/amd64. 실패하면 이미지가 생기지 않음 |
| API 모드 | `VITE_API_MODE=http`, `VITE_API_BASE_URL=`(빈 값 = 같은 출처 `/api`). 빌드에 넣는 값은 브라우저에 공개되는 이 둘뿐이고 비밀값은 넣지 않는다 |
| 빌드 맥락 | `front/`만. `front/.dockerignore`가 빌드 입력(`package*.json`·`index.html`·`vite.config.ts`·`tsconfig*.json`·`src/`)만 들인다. 로컬 `node_modules`·`dist`·`.env*`·테스트는 들어오지 않음(시험: 맥락에 심은 `.env.production`이 결과를 바꾸지 않음) |
| 소스맵 | Vite 기본값(만들지 않음). 빌드 단계에서 `.map`이 있으면 실패 |
| 필수 검사 아님 | `front-image-publish`는 경로 필터가 있어 병합 조건(`ci-result`)에 넣지 않는다(넣으면 화면을 안 바꾼 PR이 기다리게 됨). main에 연달아 Push하면 GitHub가 기다리던 앞 실행을 건너뛸 수 있어 그 커밋의 이미지는 없을 수 있다. 배포는 발행된 digest만 쓴다 |

### 화면 보안 검사 (`scan-front.sh`)

마지막 이미지에는 lockfile이 없어 이미지 검사만으로는 npm 의존성을 못 본다. 그래서 둘로 나눠 **둘 다** 통과해야 발행한다. 판정(`evaluate.sh`)과 막는 기준은 백엔드와 같다(CRITICAL, 고친 판이 있는 HIGH, 비밀값 1건 → 막음. 고친 판 없는 HIGH는 경고. 예외는 `scan-exceptions.txt`로만).

| 검사 | 대상 | 믿지 않음(3) |
|---|---|---|
| npm 의존성 | `front/package-lock.json`(Trivy fs, `--include-dev-deps`: Vite·TypeScript 같은 빌드 도구도 공급망) | Trivy 실패, npm 패키지·개발 의존성을 읽지 못함 |
| 이미지 비밀값 | 발행할 scratch 이미지의 `/site`(Trivy image `--scanners secret`) | Trivy 실패, 검사한 이미지 ID가 발행할 이미지가 아님 |
| 내용 | `check-front.sh`(위 계약) | 계약 위반은 30 |

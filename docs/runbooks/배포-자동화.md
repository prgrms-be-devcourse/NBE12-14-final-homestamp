# 자동 배포(GitHub Actions → SSM → deploy.sh) 런북

GitHub Actions가 승인된 이미지 digest로 앱 EC2의 `deploy.sh`(블루/그린, `docs/runbooks/배포-블루그린.md`)를 부르는 길이다. 설정 원본은 `.github/workflows/deploy.yml`, `.github/scripts/ssm-deploy.sh`, `infra/terraform/deploy.tf`, `infra/terraform/ssm/deploy-command.sh.tftpl`.

- 아직 실제로 돌려 보지 않았다(Terraform apply 전, Environment 없음). 가짜 aws·가짜 deploy.sh 시험과 Terraform mock 시험만 통과했다
- `deploy.sh`는 #205, nginx 전환은 #204, Migration·GRANT는 #173이다. 세 PR이 병합된 뒤에 실제로 이어 본다

```
사람: Actions → deploy → Run workflow(main, digest)
 preflight  main인지 · digest 형식 · Environment production에 승인자 + 배포 브랜치 main만     (없으면 멈춤, AWS 안 닿음)
 deploy     ── 승인자 승인(자기 승인 금지) ──
            설정 변수 확인 → 이미지 확인(공개 GHCR, digest 존재, linux/amd64)
            OIDC → homestamp-deploy 역할(1시간, 장기 키 없음)
            ssm send-command homestamp-deploy  Digest=sha256:…  → 앱 EC2 한 대
              (EC2 root) 문서 명령: digest 다시 검사 → /opt/homestamp 소유자·권한·deploy.sh 해시 검사
                                    → exec deploy.sh --config deploy.env <IMAGE_REPOSITORY>@<digest>
            get-command-invocation으로 끝날 때까지 → 서버 종료 코드 = 워크플로 결과
```

## 신뢰 경계

| 무엇 | 누가 바꿀 수 있나 | 막는 것 |
|---|---|---|
| 운영 배포 시작 | `main`의 `deploy.yml`을 실행할 수 있는 사람 + Environment 승인자 | Environment 승인(자기 승인 금지), 배포 브랜치 `main`, preflight가 규칙이 없으면 멈춤 |
| AWS 자격 증명 | OIDC로 `environment:production` job만 | 신뢰 조건 `StringEquals`, 저장소 고유 번호가 들어간 sub(이름을 바꿔도 못 맡음) |
| 서버에서 도는 명령 | Terraform(문서 내용) | 역할은 이 문서·이 서버 하나만. `AWS-RunShellScript`·`AWS-RunDocument` 등 다른 문서는 Deny. 문서에 다른 문서를 부르는 `aws:runDocument` 단계 없음. 역할에 문서 고치기 Deny |
| 문서 입력 | 워크플로 입력 | `allowedPattern ^sha256:[0-9a-f]{64}$`(API와 Agent에서 실행 전 검사) + `ENV_VAR`(명령에 끼워 넣지 않음) + 문서 명령이 한 번 더 검사 |
| `deploy.sh` 내용 | EC2 root(운영 담당이 셸로) | 문서가 해시를 Terraform 변수와 비교, root 소유·그룹/남 쓰기 금지·링크 금지 확인. 다르면 실행하지 않음(21) |
| `deploy.env` | EC2 root | 같은 소유자·권한 검사. 비밀값 없음 |
| 앱 이미지 | GHCR에 올릴 수 있는 사람 | digest만 배포, `deploy.sh`가 `IMAGE_REPOSITORY`의 이미지만 받음 |

SSM Agent는 root로 돈다. 그래서 서버에서 도는 것은 **해시가 고정된 파일 하나**뿐이어야 한다. GitHub Actions는 서버의 파일을 덮어쓰지 못한다(문서가 파일을 받거나 쓰지 않고, 역할에 다른 문서·세션이 없음).

**받아들인 한계**: 팀 IAM 사용자(공용 키, AdministratorAccess)는 문서·역할·EC2를 모두 바꿀 수 있다(04 8장 ops-admin과 같은 한계). 이 길이 막는 것은 GitHub 쪽에서 출발하는 임의 명령이다. 결과 읽기(`GetCommandInvocation`·`ListCommandInvocations`)는 AWS가 자원 범위를 지원하지 않아 계정의 다른 명령 결과도 읽을 수 있다(읽기만).

## 코드 배포와 앱 배포는 따로

| | 앱 이미지 배포 | 배포 코드(`deploy.sh`) 바꾸기 |
|---|---|---|
| 무엇 | 새 앱 이미지 digest | `infra/deploy/deploy.sh` |
| 누가 | 승인자가 승인한 `deploy.yml` | 운영 담당(ops-admin 셸) |
| 순서 | Run workflow | ① 저장소 PR 병합 ② 그 커밋의 파일을 EC2에 설치 ③ 해시를 `deploy_script_sha256`에 넣는 Terraform PR ④ apply |
| 안 맞으면 | — | 해시가 달라 문서가 실행을 거절(21). 설치와 Terraform이 둘 다 끝나야 배포가 열린다 |

설치(제안, 아직 안 함):
```sh
git -C <저장소> rev-parse HEAD                     # 병합된 커밋을 대장에 적는다
sudo install -d -o root -g root -m 0755 /opt/homestamp/deploy
sudo install -o root -g root -m 0750 <저장소>/infra/deploy/deploy.sh /opt/homestamp/deploy/deploy.sh
sudo install -o root -g root -m 0640 <채운 파일> /opt/homestamp/deploy/deploy.env   # 처음 한 번
sha256sum /opt/homestamp/deploy/deploy.sh          # → deploy_script_sha256 (Terraform PR)
```
`/opt/homestamp` 자체도 root 소유·0755여야 한다(문서가 확인).

## 처음 설정 (아직 안 함, 순서대로)

1. **Terraform**: 이 PR의 `deploy.tf`를 apply(인프라 담당). 문서·역할·정책 세 개가 생긴다. `deploy_script_sha256`이 비어 있어 처음에는 문서가 실행을 거절한다(20)
2. **Environment `production`**(저장소 Admin): Settings → Environments → New
   - Required reviewers: 승인자 1명 이상, **Prevent self-review 켬**
   - Deployment branches and tags: **Selected branches → `main` 하나**
   - 변수: `EC2_INSTANCE_ID`(앱 EC2), `IMAGE_REPOSITORY`(`ghcr.io/…`, 정해진 뒤). 비밀값은 두지 않는다(계정 번호는 기존 저장소 Secret `AWS_ACCOUNT_ID`)
3. **EC2**: 위 "설치" → 해시 Terraform PR → apply
4. **이미지**: GHCR 패키지를 공개로(04 9-3). 이미지는 `linux/amd64`(t3)
5. 첫 실행은 이미 활성인 이미지로(결과 noop)부터 해서 길을 확인한다

승인자는 아직 정하지 않았다(운영 담당 + 1명 제안). GitHub Free 조직의 **공개 저장소**라 required reviewers를 쓸 수 있다. 쓸 수 없게 되면 자동 배포로 바꾸지 않고, 운영 담당이 ops-admin으로 같은 SSM 문서를 손으로 보내는 방법으로 대신한다(아래).

## 실행

Actions → **deploy** → Run workflow → 브랜치 `main`, digest `sha256:…` → 승인자 승인 → 결과.

| 워크플로 종료 코드 | 뜻 |
|---|---|
| 0 | 성공, 또는 이미 같은 이미지(noop) |
| 2·3·4·5·10~17 | 서버 `deploy.sh`의 코드 그대로(배포-블루그린.md 종료 코드 표). 3은 다른 배포 중 |
| 20 | 문서에 승인된 `deploy.sh` 해시가 없음(Terraform 변수) |
| 21 | 서버 파일의 소유자·권한·해시가 다름(변조 또는 설치 미완료) → 실행하지 않음 |
| 30 | SSM 명령을 보내지 못함(권한 거부, 문서·인스턴스 이름) |
| 40 | 서버 실행 900초 초과. Agent가 `deploy.sh`를 멈춤 → EC2에서 `--status` |
| 41 | 전달 실패: EC2가 꺼져 있거나 SSM 연결 없음(60초). 켠 뒤 다시 실행(04 8장) |
| 42 | 명령이 취소됨 |
| 43 | 워크플로가 기다리기를 그만둠. **서버 명령은 계속 돌 수 있다** |
| 130 | 워크플로 취소. 서버 배포는 끝까지 돈다 |

- **동시 실행**: `concurrency: deploy-production`(진행 중인 것은 취소하지 않고 다음 것이 기다림) + 서버 `flock`(3)
- **다시 실행**: 같은 digest로 다시 돌리면 이미 활성이면 noop, 중간에 실패했으면 처음부터 안전하게 다시 한다(`deploy.sh`가 upstream으로 활성을 다시 읽음)
- **취소**: 워크플로를 취소해도 서버 명령은 취소하지 않는다(취소 권한을 주지 않음). Migration 중에 끊으면 더 위험하기 때문이다. 결과는 EC2에서 `deploy.sh --status`로
- 출력: 서버의 `deploy.sh` 단계 문장(비밀값 없음, 앱 로그 없음)만 워크플로에 보인다. SSM 출력은 앞부분 2만4천 자까지

## Environment 승인을 쓸 수 없을 때 (대안)

자동 운영 배포로 바꾸지 않는다. 운영 담당이 ops-admin 역할로 같은 문서를 손으로 보낸다(ops-admin에 이 문서의 SendCommand를 더하는 PR이 필요, 지금은 없음):
```sh
aws ssm send-command --profile homestamp-ops-admin --region ap-northeast-2 \
  --document-name homestamp-deploy --instance-ids <EC2> --parameters Digest=sha256:<64자> --timeout-seconds 60
```
같은 해시 검사·`deploy.sh`를 거친다. 실행 기록은 대장에.

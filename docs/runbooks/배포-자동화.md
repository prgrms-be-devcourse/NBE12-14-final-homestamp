# 자동 배포(GitHub Actions → SSM → deploy.sh) 런북

GitHub Actions가 승인된 이미지 digest로 앱 EC2의 `deploy.sh`(블루/그린, `docs/runbooks/배포-블루그린.md`)를 부르는 길이다. 설정 원본은 `.github/workflows/deploy.yml`, `.github/scripts/ssm-deploy.sh`, `infra/terraform/deploy.tf`, `infra/terraform/ssm/deploy-command.sh.tftpl`.

- 아직 실제로 돌려 보지 않았다(Terraform apply 전, Environment 없음). 가짜 aws·가짜 deploy.sh 시험과 Terraform mock 시험만 통과했다
- `deploy.sh`는 #205, nginx 전환은 #204, 이미지 발행은 #207, GRANT 실행기는 #299다. 병합된 뒤 실제로 이어 볼 것:
  - 실제 upstream 대상 확인(전환 뒤 401만이 아니라 어느 슬롯이 응답했는지)
  - 실제 PostgreSQL + 발행 이미지 + Nginx로 한 번 끝까지(noop부터)
  - DB 준비(Role Bootstrap·Migration 로그인) 뒤 `--migrate`·`--apply-grants`
  - 두 앱이 함께 뜬 동안 Poller 동시 실행(SKIP LOCKED)
  - Blue/Green 사이 스키마·권한·API 호환(Expand–Contract)
  - EC2 자원(두 앱 + Migration 컨테이너가 함께 뜰 때 메모리)

```
사람: Actions → deploy → Run workflow(main, digest)
 preflight  main인지 · digest 형식 · Environment production에 승인자 + 자기 승인 금지 + Admin 우회 금지 + 배포 브랜치 main만 (없으면 멈춤, AWS 안 닿음)
 deploy     ── 승인자 승인(자기 승인 금지) ──
            설정 변수 확인 → 이미지 확인(check-image.sh: 공개 GHCR, 원문 digest 재계산, linux/amd64,
                             커밋 라벨, 발행 태그 sha-<커밋> = 이 digest, 그 커밋이 main에 있음)
            OIDC → homestamp-deploy 역할(1시간, 장기 키 없음)
            ssm send-command homestamp-deploy  Digest=sha256:…  → 앱 EC2 한 대
              (EC2 root) 문서 명령: digest 다시 검사 → /opt/homestamp 소유자·권한·deploy.sh 해시 검사
                                    → deploy.sh --config deploy.env <IMAGE_REPOSITORY>@<digest>
                                      (받은 신호를 넘기고, 출력은 끝 20,000바이트만)
            get-command-invocation으로 끝날 때까지(최대 2700초) → 서버 종료 코드 = 워크플로 결과
            요약(Job summary): 실행 ID · digest · SSM 명령 ID · 상태 · 종료 코드 · 결과(성공/변경 없음/실패)
```

## 신뢰 경계

| 무엇 | 누가 바꿀 수 있나 | 막는 것 |
|---|---|---|
| 운영 배포 시작 | `main`의 `deploy.yml`을 실행할 수 있는 사람 + Environment 승인자 | Environment 승인(자기 승인 금지), Admin 우회 금지, 배포 브랜치 `main`. preflight(`.github/scripts/preflight.sh`)가 셋 중 하나라도 없으면 멈춤 |
| AWS 자격 증명 | OIDC로 `environment:production` job만 | 신뢰 조건 `StringEquals`, 저장소 고유 번호가 들어간 sub(이름을 바꿔도 못 맡음) |
| 서버에서 도는 명령 | Terraform(문서 내용) | 역할은 이 문서·이 서버 하나만. `AWS-RunShellScript`·`AWS-RunDocument` 등 다른 문서는 Deny. 문서에 다른 문서를 부르는 `aws:runDocument` 단계 없음. 역할에 문서 고치기 Deny |
| 문서 입력 | 워크플로 입력 | `allowedPattern ^sha256:[0-9a-f]{64}$`(API와 Agent에서 실행 전 검사) + `ENV_VAR`(명령에 끼워 넣지 않음) + 문서 명령이 한 번 더 검사 |
| `deploy.sh` 내용 | EC2 root(운영 담당이 셸로) | 문서가 해시를 Terraform 변수와 비교, root 소유·그룹/남 쓰기 금지·링크 금지 확인. 다르면 실행하지 않음(21) |
| nginx 전환기(`SWITCH_CMD`, #204 `switch-upstream.sh`) | EC2 root | `deploy.sh`가 root로 부른다. **해시는 고정하지 않는다**. 문서가 `deploy.env`를 `deploy.sh`와 같은 방식(마지막 `SWITCH_CMD=` 줄, 없으면 기본값)으로 읽어 `/opt/homestamp` 아래 일반 실행 파일인지, 파일부터 `/`까지 root 소유·그룹/남 쓰기 금지·링크 금지인지 본다. 다르면 21 |
| `deploy.env` | EC2 root | 같은 소유자·권한 검사. 비밀값 없음 |
| 앱 이미지 | GHCR에 올릴 수 있는 사람 | digest만 배포, `deploy.sh`가 `IMAGE_REPOSITORY`의 이미지만 받음. 워크플로가 이 조직의 `ghcr.io`인지, 발행 절차(#207)의 태그·커밋 라벨과 맞고 그 커밋이 `main`에 있는지 본다(**서명·빌드 증명 검증은 아님**. GHCR 쓰기 권한이 있는 사람이 태그를 손으로 바꾸면 막지 못한다) |

SSM Agent는 root로 돈다. 그래서 서버에서 도는 것은 **해시가 고정된 파일 하나**뿐이어야 한다. GitHub Actions는 서버의 파일을 덮어쓰지 못한다(문서가 파일을 받거나 쓰지 않고, 역할에 다른 문서·세션이 없음).

**받아들인 한계**: 팀 IAM 사용자(공용 키, AdministratorAccess)는 문서·역할·EC2를 모두 바꿀 수 있다(04 8장 ops-admin과 같은 한계). 이 길이 막는 것은 GitHub 쪽에서 출발하는 임의 명령이다. 결과 읽기(`GetCommandInvocation`·`ListCommandInvocations`)는 AWS가 자원 범위를 지원하지 않아 계정의 다른 명령 결과도 읽을 수 있다(읽기만).

## 코드 배포와 앱 배포는 따로

| | 앱 이미지 배포 | 배포 코드(`deploy.sh`) 바꾸기 |
|---|---|---|
| 무엇 | 새 앱 이미지 digest | `infra/deploy/deploy.sh` |
| 누가 | 승인자가 승인한 `deploy.yml` | 운영 담당(ops-admin 셸) |
| 순서 | Run workflow | ① 저장소 PR 병합 ② 그 커밋의 파일을 EC2에 설치 ③ 해시를 `deploy_script_sha256`에 넣는 Terraform PR ④ apply |
| 안 맞으면 | — | 해시가 달라 문서가 실행을 거절(21). 설치와 Terraform이 둘 다 끝나야 배포가 열린다 |

설치(제안, 아직 안 함):
```sh
git -C <저장소> rev-parse HEAD                     # 병합된 커밋을 대장에 적는다
sudo install -d -o root -g root -m 0755 /opt/homestamp/deploy
sudo install -o root -g root -m 0750 <저장소>/infra/deploy/deploy.sh /opt/homestamp/deploy/deploy.sh
sudo install -o root -g root -m 0640 <채운 파일> /opt/homestamp/deploy/deploy.env   # 처음 한 번
sha256sum /opt/homestamp/deploy/deploy.sh          # → deploy_script_sha256 (Terraform PR)
```
`/opt/homestamp` 자체도 root 소유·0755여야 한다(문서가 확인).

## 처음 설정 (아직 안 함, 순서대로)

1. **Terraform**: 이 PR의 `deploy.tf`를 apply(인프라 담당). 문서·역할·정책 세 개가 생긴다. `deploy_script_sha256`이 비어 있어 처음에는 문서가 실행을 거절한다(20)
2. **Environment `production`**(저장소 Admin): Settings → Environments → New
   - Required reviewers: 승인자 1명 이상, **Prevent self-review 켬**
   - **Allow administrators to bypass configured protection rules 끔**(기본값은 켜짐. 켜져 있으면 Admin이 승인 없이 배포할 수 있어 preflight가 멈춤)
   - Deployment branches and tags: **Selected branches → `main` 하나**
   - 변수: `EC2_INSTANCE_ID`(앱 EC2), `IMAGE_REPOSITORY`(`ghcr.io/…`, 정해진 뒤). 비밀값은 두지 않는다(계정 번호는 기존 저장소 Secret `AWS_ACCOUNT_ID`)
3. **EC2**: 위 "설치" → 해시 Terraform PR → apply
4. **이미지**: GHCR 패키지를 공개로(04 9-3). 이미지는 `linux/amd64`(t3)
5. 첫 실행은 이미 활성인 이미지로(결과 noop)부터 해서 길을 확인한다

승인자는 아직 정하지 않았다(운영 담당 + 1명 제안). GitHub Free 조직의 **공개 저장소**라 required reviewers를 쓸 수 있다. 쓸 수 없게 되면 자동 배포로 바꾸지 않고, 운영 담당이 ops-admin으로 같은 SSM 문서를 손으로 보내는 방법으로 대신한다(아래).

## 시간 제한

`deploy.sh`(#205) 기본 설정의 가장 긴 길(되돌리기까지)은 **약 1490초 + 이미지 받기**다. 보장된 최대값이 아니라 기본값으로 더한 추정이다:

| 단계 | 기본값 | 설정 |
|---|---|---|
| `--migrate` | 900초(넘으면 멈춤 30초) | `MIGRATE_TIMEOUT`, `STOP_TIMEOUT` |
| `--apply-grants` | 300초(넘으면 멈춤 30초) | `GRANTS_TIMEOUT` |
| 헬스 | 120초 | `HEALTH_TIMEOUT` |
| 전환(reload 뒤 이전 nginx 작업 프로세스 끝 기다림) | 45초(nginx `worker_shutdown_timeout 30s`) | `RELOAD_WAIT` |
| 전환 뒤 확인 | 20초 + 요청 하나 5초 | `VERIFY_TIMEOUT` |
| 되돌리기 전환 + 확인 | 45 + 25초 | 위와 같음 |
| 새 앱(또는 이전 앱) 멈춤 | 30초 | `STOP_TIMEOUT` |
| 같은 이미지(noop) 확인 | 헬스 20 + 확인 25초(이 길에서는 Migration이 없음) | `VERIFY_TIMEOUT` |
| 이미지 받기 | **`deploy.sh` 안에 제한 없음** | 문서 실행 2400초가 끝 |

Migration·GRANT의 멈춤 30초는 그 단계가 시간 초과로 실패하는 길에만 더해지고 뒤 단계와 겹치지 않는다(그래서 합이 약 1490초). 확인·헬스는 끝 시각 뒤 요청 한 번(최대 5초)이 더 돌 수 있다. 문서 실행 2400초까지 약 900초가 이미지 받기·기록에 남는다. 안쪽 제한이 바깥보다 늘 짧게 둔다. **`RELOAD_WAIT`·`MIGRATE_TIMEOUT` 같은 값을 운영에서 바꾸면 이 표와 문서 실행 2400초·결과 기다림 2700초·job 50분·OIDC 3600초를 함께 다시 본다.**

| 제한 | 값 | 있는 곳 | 이유 |
|---|---|---|---|
| 전달 | 60초 | `ssm-deploy.sh` `--timeout-seconds` | EC2가 꺼져 있으면 기다리지 않음(04 8장) |
| 문서 실행 | 2400초 | `deploy.tf` `timeoutSeconds` | 위 약 1490초 + 이미지 받기 여유. 넘으면 Agent가 신호 → `deploy.sh`가 interrupted로 기록(40) |
| 결과 기다림 | 2700초 | `ssm-deploy.sh` `POLL_LIMIT` | 문서 실행 2400 + 전달 60 + 여유. 그만둬도 서버 명령은 계속(43) |
| job | 50분 | `deploy.yml` `timeout-minutes` | 기다림 45분 + 앞 단계 |
| OIDC 세션 | 3600초 | `role-duration-seconds`, 역할 `max_session_duration` | job 50분 안. 역할 상한은 그대로 |

## 실행

Actions → **deploy** → Run workflow → 브랜치 `main`, digest `sha256:…` → 승인자 승인 → 결과. Job summary에 실행 ID·digest·SSM 명령 ID·상태·종료 코드·결과가 남는다(비밀값·접속 주소·환경변수 없음). SSM 보내기가 성공했다고 배포가 성공한 것이 아니다: 결과는 서버 종료 코드와 `deploy.sh` 결과 줄로만 정한다.

| 워크플로 종료 코드 | 뜻 | 할 일 |
|---|---|---|
| 0 | 성공, 또는 이미 같은 이미지(요약에 "변경 없음"). 결과 줄을 못 찾으면 경고. 코드 0인데 결과 줄이 failed·interrupted면 1로 실패 | — |
| 2·4·10·13·14·15 | 서버 `deploy.sh`의 코드 그대로(배포-블루그린.md 종료 코드 표) | 원인 확인 뒤 사람이 다시 |
| 3 | 다른 배포가 서버에서 진행 중 | 끝난 뒤 다시 |
| 5 | 이전 Migration·GRANT 컨테이너가 아직 실행 중 | 끝난 뒤 다시 |
| 11·12 | `--migrate`·`--apply-grants` 실패·시간 초과. 새 앱은 시작하지 않음. 이미 적용된 V 파일·권한은 남음 | **자동 재시도 없음**. 원인을 본 뒤 사람이 |
| 16 | 전환 뒤 확인 실패: 이전 슬롯으로 되돌림(첫 배포면 새 앱 그대로) | 기록의 `rolled_back` 확인 |
| 17 | **되돌리기를 확인하지 못함. 두 앱이 떠 있고 트래픽이 새 슬롯일 수 있음** | **운영자 확인 필요**. 다시 배포하지 말고 배포-블루그린.md "손으로 되돌리기" |
| 129·130·143 | `deploy.sh`가 신호로 멈춤(문서 실행 시간 초과 포함) | EC2에서 `--status` |
| 20 | 문서에 승인된 `deploy.sh` 해시가 없음(Terraform 변수) | 해시 PR |
| 21 | 서버 파일(`deploy.sh`·`deploy.env`·전환기)의 소유자·권한·해시가 다름(변조 또는 설치 미완료) → 실행하지 않음 | 설치 확인 |
| 30 | SSM 명령을 보내지 못함(권한 거부, 문서·인스턴스 이름) | 설정 확인 |
| 40 | 서버 실행 2400초 초과. Agent가 `deploy.sh`를 멈춤(받은 신호를 넘기고 그때까지의 출력 끝을 바로 냄. Agent가 강제 종료하면 출력이 없을 수 있음) | EC2에서 `--status` |
| 41 | 전달 실패: EC2가 꺼져 있거나 SSM 연결 없음(60초) | 켠 뒤 다시(04 8장) |
| 42 | 명령이 취소됨(누군가 AWS에서 취소) | EC2에서 `--status` |
| 43 | 워크플로가 기다리기를 그만둠. **서버 명령은 계속 돌 수 있다** | 요약의 명령 ID로 확인, EC2에서 `--status` |
| 44 | 결과를 한 번도 조회하지 못함(권한·네트워크). **서버 명령은 돌고 있을 수 있다** | 같음 |
| 50~54 | 이미지 확인 실패(없음·원문 다름 / amd64 아님 / 커밋 라벨 없음 / 발행 태그가 다른 이미지 / 커밋이 `main`에 없음). AWS에 닿기 전 | 발행 절차로 올린 digest인지 |
| 130 | 워크플로 취소. 서버 배포는 끝까지 돈다 | 요약의 명령 ID, EC2에서 `--status` |

결과 조회는 보낸 직후의 `InvocationDoesNotExist`를 조용히 다시 묻고, 다른 조회 실패는 경고를 남기고 다시 묻는다(Pending·InProgress·Delayed도 계속 기다림). 끝난 상태는 Success·Failed·TimedOut·Cancelled·전달 실패로 나눈다. 워크플로는 실패한 배포를 다시 보내지 않는다.

- **동시 실행**: `concurrency: deploy-production`(진행 중인 것은 취소하지 않고 다음 것이 기다림) + 서버 `flock`(3)
- **다시 실행**: 같은 digest로 다시 돌리면 이미 활성이면 noop, 중간에 실패했으면 처음부터 안전하게 다시 한다(`deploy.sh`가 upstream으로 활성을 다시 읽음)
- **취소**: 워크플로를 취소해도 서버 명령은 취소하지 않는다(취소 권한을 주지 않음). Migration 중에 끊으면 더 위험하기 때문이다. 결과는 EC2에서 `deploy.sh --status`로
- 출력: 서버의 `deploy.sh` 단계 문장과 Migration·GRANT 출력 끝 100줄(비밀값·접속 주소 없음, 앱 로그 없음)만 워크플로에 보인다. SSM은 출력 앞 2만4천 자만 돌려주므로 문서 명령이 `deploy.sh` 출력의 **끝** 20,000바이트만 내서 마지막 결과 줄이 남게 한다. 전체는 EC2의 `deploy.sh` 기록
- 로그에 남기지 않는 것: 비밀값·JDBC URL·키·Migration 파일 내용·환경변수 전체·TLS 키·개인정보. 스크립트는 `set +x`로 시작하고 환경을 출력하지 않는다

| 칸 | 뜻 |
|---|---|
| 번들 위치 | 빌드 결과(`front/dist`)를 받을 곳. 아직 정하지 않음(#204 Nginx가 내보낼 경로와 맞춤) |
| 커밋 | 빌드한 `main` 커밋 40자(백엔드 이미지의 커밋 라벨과 같은 방식) |
| SHA-256 | 번들 압축 파일의 해시. 서버가 받은 뒤 같은지 보고 다르면 바꾸지 않음 |

프론트를 서버에 올리는 길이 없으면 **첫 공개 배포를 하지 않는다**(남은 막는 일).

## Environment 승인을 쓸 수 없을 때 (대안)

자동 운영 배포로 바꾸지 않는다. 운영 담당이 ops-admin 역할로 같은 문서를 손으로 보낸다(ops-admin에 이 문서의 SendCommand를 더하는 PR이 필요, 지금은 없음):
```sh
aws ssm send-command --profile homestamp-ops-admin --region ap-northeast-2 \
  --document-name homestamp-deploy --instance-ids <EC2> --parameters Digest=sha256:<64자> --timeout-seconds 60
```
같은 해시 검사·`deploy.sh`를 거친다. 실행 기록은 대장에.

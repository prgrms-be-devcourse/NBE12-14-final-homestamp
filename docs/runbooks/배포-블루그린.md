# 블루/그린 배포 런북

앱 EC2(`homestamp-web`) 한 대에서 새 앱 이미지를 끊김 없이 바꾸는 절차다. 실행기는 `infra/deploy/deploy.sh` 하나이고, CD(`deploy.yml`, 04 9-2)가 SSM 문서로 부른다. 손으로 부를 때도 같은 스크립트를 쓴다.

- 이 문서는 아직 실제 EC2에서 돌려 보지 않았다. 로컬 격리 시험(`infra/deploy/test/local-test.sh`, 가짜 앱·가짜 nginx 전환기)만 통과했다
- 실제 Migration 이미지(#173)와 nginx 전환기(`infra/nginx/switch-upstream.sh`, #204)와의 연결 확인은 두 PR이 병합된 뒤에 한다(아래 "병합 뒤 통합")

```
CD ── SSM ──▶ deploy.sh <저장소>@sha256:<digest>
               1 잠금(flock, 진행 중이면 거절)
               2 활성 슬롯 = nginx upstream 파일이 가리키는 주소
               3 이미지 받기(digest 확인)          같은 이미지가 이미 활성이면 여기서 끝(noop)
               4 --migrate      (일회성, 0 아니면 멈춤)
               5 --apply-grants (일회성, 0 아니면 멈춤)
               6 비활성 슬롯에 새 앱(127.0.0.1:8081 또는 8082 → 8080)
               7 /actuator/health 200 + UP (120초)
               8 switch-upstream.sh → nginx -t → reload
               9 전환 뒤 확인(nginx를 거친 요청에 앱이 답함)   실패하면 이전 슬롯으로 되돌림
              10 이전 앱 멈춤(지우지 않음) → 기록 → 잠금 풀림
```

## 슬롯과 포트 (운영 계약)

| 슬롯 | 컨테이너 | 호스트 → 컨테이너 | 관리 포트 |
|---|---|---|---|
| blue | `homestamp-app-blue` | `127.0.0.1:8081` → 8080 | 9091(아직 앱에 없음, 아래 후속) |
| green | `homestamp-app-green` | `127.0.0.1:8082` → 8080 | 9092(같음) |

- 앱 포트는 `127.0.0.1`에만 묶는다. 바깥에서는 nginx(80·443)로만 들어온다. 8081·8082는 다른 서비스(nginx 80·443, 관리 포트 9091·9092)와 겹치지 않고 보안 그룹에도 열지 않는다
- **어느 슬롯이 활성인지는 nginx upstream 파일(`/opt/homestamp/nginx/run/upstream/upstream.conf`)만 기준이다.** 트래픽이 실제로 가는 곳이기 때문이다. 이 파일이 blue·green 주소가 아니면 추측하지 않고 멈춘다(종료 4)
- nginx를 처음 설치하면 `render.sh`가 upstream을 8081(blue)로 만들어 두므로, 실제 첫 배포는 "blue를 가리키지만 blue 앱은 없음" 상태에서 green으로 간다. 정상이다

## 앱 컨테이너 실행 계약

| 항목 | 값 | 근거 |
|---|---|---|
| 이미지 | `IMAGE_REPOSITORY@sha256:<64자>`만. 태그만이면 거절. 받은 뒤 RepoDigests로 다시 확인 | 태그는 다시 쓸 수 있다. 같은 입력이 언제나 같은 이미지 |
| 설정·비밀값 | `SPRING_PROFILES_ACTIVE=prod`, `TZ=UTC`만 넘긴다. 앱이 EC2 역할로 SSM `/homestamp/prod/app/`을 직접 읽는다 | 04 6장. 비밀값을 환경변수로 넘기면 `docker inspect`에 보인다. 컨테이너에서 IMDSv2에 닿도록 EC2 hop limit은 2(`ec2.tf`) |
| Flyway | 앱은 Flyway를 돌리지 않는다(prod 프로필 `spring.flyway.enabled=false`, #173). 스키마는 4단계 `--migrate`만 바꾼다 | 04 6장 |
| 메모리 | `--memory=800m`, 이미지의 `-XX:MaxRAMPercentage=60` | 04 8장 |
| 재시작 | `--restart unless-stopped`. 손으로 멈춘 이전 앱은 재부팅해도 다시 뜨지 않는다 | 04 7장 |
| 격리 | 읽기 전용 루트, `/tmp`만 tmpfs, `--cap-drop ALL`, `no-new-privileges`, 비밀 폴더를 묶지 않음 | |
| 로그 | Docker json-file 10MB×3. 배포 출력에는 앱 로그를 옮기지 않는다(`docker logs homestamp-app-<슬롯>`) | 04 8장 "디스크" |
| 정상 종료 | `docker stop -t 30`(SIGTERM 뒤 30초) | 04 8장 `server.shutdown=graceful` |

Migration·GRANT 컨테이너(`homestamp-app-migrate`, `homestamp-app-grants`)는 같은 이미지를 `--rm`, `--user $MIGRATION_UID`, 읽기 전용 루트, 권한 없음으로 돌리고 `/run/secrets/homestamp-migration`을 **읽기 전용으로 묶기만** 한다. `deploy.sh`는 그 폴더가 있는지만 보고 내용은 읽지 않는다(#173 계약: 정확히 4개 파일).

## 헬스 체크

- 새 슬롯의 `http://127.0.0.1:<8081|8082>/actuator/health`가 **200이고 본문에 `"status":"UP"`**일 때만 통과. 3초 제한으로 3초마다, 최대 `HEALTH_TIMEOUT`(120초)
- 이 경로는 앱에 실제로 있다(Actuator 기본 노출, SecurityConfig가 허용). 전체 상태에 **DB 지표가 들어 있어 DB에 닿지 못하면 DOWN·503**이라 통과하지 못한다. SSM 값이 모자라 앱이 뜨지 않으면 컨테이너가 멈추고 바로 실패(종료 13)
- 바깥에서는 nginx가 `/actuator`를 404로 막는다(#204). 헬스 체크는 nginx를 거치지 않고 앱 포트로 직접 한다
- readiness 그룹(`/actuator/health/readiness`)은 앱에서 켜지 않아 **지금은 없는 경로**다. 켜면 이 스크립트의 경로를 바꾼다

## 전환 뒤 확인과 되돌리기

- 전환이 성공하면 upstream 파일이 새 슬롯인지 보고, `POST_SWITCH_URL`(`https://homestamp.cloud/api/`, `--resolve`로 이 서버의 nginx)에 요청한다. **100~499면 앱이 답한 것**(인증이 없어 401이어도 통과), 502·503·504·연결 실패면 실패. 2초 간격 3번
- 실패하면 이전 앱이 실행 중일 때 `switch-upstream.sh`로 이전 슬롯으로 되돌리고 새 앱을 멈춘다(종료 16, `rolled_back:true`). 되돌리기도 실패하면 두 앱을 모두 남기고 종료 17
- **되돌려도 DB는 그대로다.** 전환과 되돌리기 사이(수 초) 새 앱이 받은 요청의 쓰기, 그리고 4·5단계의 Migration·GRANT는 남는다. 그래서 스키마는 언제나 이전 앱과도 맞게 쓴다(04 8장 "스키마 변경": 추가 먼저, 삭제는 다음 배포). 지우는 Migration이 있는 배포 전에는 RDS 수동 스냅숏(04 8장)

## 잠금과 다시 실행

- `flock -n /run/lock/homestamp-deploy.lock`으로 배포 전체(잠금 획득부터 기록까지)를 하나만 돌린다. 기다리지 않고 거절한다(CD가 다시 실행). GitHub Actions의 `concurrency`와 별개로 서버에서 한 번 더 막는다
- 잠금은 프로세스가 끝나면(강제 종료 포함) 커널이 푼다. `/run`은 재부팅하면 비므로 잠금 파일도 사라진다
- 강제 종료(`kill -9`, SSM 시간 초과)되면 `in-progress.json`이 남는다. 다음 실행이 이것을 `interrupted`로 기록에 옮긴다. 그때 떠 있던 Migration 컨테이너는 계속 돈다 → 다음 실행은 그것이 끝날 때까지 종료 5(Migration을 중간에 죽이지 않는다)
- 다시 실행은 언제나 안전하다: 활성은 upstream 파일로 다시 읽고, 비활성 슬롯의 컨테이너(멈춘 이전 앱, 실패해 남긴 앱)는 지우고 새로 만든다. 활성 슬롯 컨테이너는 지우지 않는다

## 재부팅 뒤

- nginx(`restart: unless-stopped`)와 활성 앱(`unless-stopped`)은 Docker가 다시 띄운다. 손으로 멈춘 이전 앱은 뜨지 않는다. upstream 파일은 디스크에 남아 같은 슬롯을 가리킨다
- 확인: `sudo /opt/homestamp/deploy/deploy.sh --status` → `active:`와 각 슬롯 상태, 마지막 기록
- 아침에 RDS가 늦게 켜지면 활성 앱의 헬스가 잠시 DOWN일 수 있다(앱이 DB 연결을 재시도, 04 7장). 이것은 배포 실패가 아니다

| 위치 | 권한 | 내용 |
|---|---|---|
| `/var/lib/homestamp/deploy/history.jsonl` | 폴더 0750 root, 파일 0640 | 배포마다 한 줄: `deploy_id`, `image`(digest), `started_at`, `finished_at`, `result`(success·noop·failed·interrupted), `exit_code`, `failed_step`, `prev_slot`, `prev_running`, `active_slot`, `rolled_back`, `db_changes_rolled_back:false` |

비밀값·토큰·DB 주소는 기록하지 않는다(스크립트가 그 값을 갖지 않는다). `set +x`. 기록은 지우지 않고 쌓는다(한 줄 약 400바이트).

## 설치 (한 번)

```sh
sudo mkdir -p /opt/homestamp/deploy
sudo cp <저장소>/infra/deploy/deploy.sh /opt/homestamp/deploy/ && sudo chmod 0750 /opt/homestamp/deploy/deploy.sh
sudo cp <저장소>/infra/deploy/deploy.env.example /opt/homestamp/deploy/deploy.env   # 필수값 채우기
sudo /opt/homestamp/deploy/deploy.sh --status
```
필요한 명령: `bash`, `docker`, `curl`, `flock`(Amazon Linux 2023 기본 util-linux). 필수 설정 `IMAGE_REPOSITORY`·`MIGRATION_UID`가 비어 있으면 멈춘다(종료 2).

## 손으로 되돌리기 (종료 17, 또는 배포가 끝난 뒤 문제를 발견했을 때)

```sh
sudo flock -n /run/lock/homestamp-deploy.lock bash         # 잠금을 쥔 셸(실패하면 배포 중). 아래는 이 셸 안에서
sudo /opt/homestamp/deploy/deploy.sh --status               # active와 이전 슬롯 확인
docker start homestamp-app-<이전>                           # 멈춰 둔 이전 앱(지우지 않고 남아 있음)
curl -fsS http://127.0.0.1:<이전 포트>/actuator/health      # {"status":"UP"} 될 때까지
sudo /opt/homestamp/nginx/switch-upstream.sh 127.0.0.1:<이전 포트>
docker stop -t 30 homestamp-app-<지금>
```
- 이전 앱이 지금 스키마에서 도는지는 "스키마는 이전 앱과도 맞게" 규칙에 달렸다. 지우는 Migration 뒤라면 되돌리지 말고 고친 이미지로 앞으로 배포한다
- 되돌린 일은 대장에 적는다(`history.jsonl`에는 남지 않는다)

## upstream을 모름 (종료 4)

`cat /opt/homestamp/nginx/run/upstream/upstream.conf`. 손으로 고쳤거나 다른 주소면, 실제로 응답하는 슬롯을 헬스로 확인한 뒤 `switch-upstream.sh 127.0.0.1:<그 포트>`로 바로잡고 다시 배포한다.

## 병합 뒤 통합 (아직 안 함)

- **#173 병합 뒤**: 실제 앱 이미지로 `--migrate`·`--apply-grants`·앱 시작을 로컬 PostgreSQL에서 한 번(읽기 전용 루트·`--cap-drop ALL`에서 앱이 뜨는지, 종료 코드가 그대로 전달되는지)
- **#204 병합 뒤**: 실제 `switch-upstream.sh`와 nginx로 전환·reload 실패·되돌리기를 같은 시험에 연결(지금은 같은 약속의 가짜 전환기)
- **정할 것**: Migration 비밀 폴더를 누가 어떻게 만드는지와 `MIGRATION_UID`(#185·#203 쪽), GHCR 저장소 이름, SSM 배포 문서와 `deploy.yml`
- **관리 포트**: 04 11장은 "배포 스크립트가 blue 9091, green 9092로 연결"이라고 하지만 앱에 `management.server.port`가 아직 없다. 앱에 생기면 사설 IP에 묶는 방법과 함께 이 스크립트에 넣는다

## 시험 (로컬, AWS 없음)

```sh
mkdir -p /tmp/hs-deploy-work && infra/deploy/test/local-test.sh /tmp/hs-deploy-work   # 빈 폴더를 준다
```
Linux 컨테이너(bash·util-linux `flock`·curl·docker CLI)에서 `deploy.sh`를 그대로 돌리고, 가짜 앱 이미지를 시험용 로컬 레지스트리에 올려 digest로 받는다. 96개: 입력 거절, 첫 배포, blue→green, green→blue, 같은 이미지(noop), Migration 실패, GRANT 실패, 시작 실패, 헬스 실패, nginx 검사 실패, reload 실패, 전환 뒤 확인 실패와 되돌리기, 동시 배포, 강제 종료와 다시 실행, 재부팅 흉내, 모르는 upstream, 비밀값(canary)이 출력·기록·`docker inspect`에 없음, 기록 형식·권한. 이름이 `hs-deploy-test-`인 컨테이너·이미지만 만들고 끝나면 지운다.

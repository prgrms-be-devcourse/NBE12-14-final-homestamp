# 블루/그린 배포 런북

앱 EC2(`homestamp-web`) 한 대에서 새 앱 이미지를 끊김 없이 바꾸는 절차다. 실행기는 `infra/deploy/deploy.sh` 하나이고, CD(`deploy.yml`, 04 9-2)가 SSM 문서로 부른다. 손으로 부를 때도 같은 스크립트를 쓴다.

- 이 문서는 아직 실제 EC2에서 돌려 보지 않았다. 로컬 격리 시험(`infra/deploy/test/local-test.sh`, 가짜 앱·가짜 nginx 전환기)만 통과했다
- 실제 Migration 이미지(#173)와 nginx 전환기(`infra/nginx/switch-upstream.sh`, #204)와의 연결 확인은 두 PR이 병합된 뒤에 한다(아래 "병합 뒤 통합")

```
CD ── SSM ──▶ deploy.sh <저장소>@sha256:<digest>
               1 잠금(flock, 진행 중이면 거절)
               2 활성 슬롯 = nginx upstream 파일이 가리키는 주소
               3 이미지 받기(digest 확인)          같은 이미지가 활성이면 헬스·전환 뒤 확인을 통과할 때만 끝(noop), 아니면 4
               4 --migrate      (일회성, 0 아니면 멈춤)
               5 --apply-grants (일회성, 0 아니면 멈춤)
               6 비활성 슬롯에 새 앱(127.0.0.1:8081 또는 8082 → 8080)
               7 /actuator/health 200 + UP (120초)
               8 switch-upstream.sh → nginx -t → reload
               9 전환 뒤 확인(nginx를 거친 요청에 앱이 답함)   실패하면 이전 슬롯으로 되돌림
              10 이전 앱 멈춤(지우지 않음) → 기록 → 잠금 풀림
```

## 슬롯과 포트 (운영 계약)

| 슬롯 | 컨테이너 | 호스트 → 컨테이너 | 관리 포트 |
|---|---|---|---|
| blue | `homestamp-app-blue` | `127.0.0.1:8081` → 8080 | 9091(아직 앱에 없음, 아래 후속) |
| green | `homestamp-app-green` | `127.0.0.1:8082` → 8080 | 9092(같음) |

- 앱 포트는 `127.0.0.1`에만 묶는다. 바깥에서는 nginx(80·443)로만 들어온다. 8081·8082는 다른 서비스(nginx 80·443, 관리 포트 9091·9092)와 겹치지 않고 보안 그룹에도 열지 않는다
- **어느 슬롯이 활성인지는 nginx upstream 파일(`/opt/homestamp/nginx/run/upstream/upstream.conf`)만 기준이다.** 트래픽이 실제로 가는 곳이기 때문이다. 이 파일이 blue·green 주소가 아니면 추측하지 않고 멈춘다(종료 4)
- nginx를 처음 설치하면 `render.sh`가 upstream을 8081(blue)로 만들어 두므로, 실제 첫 배포는 "blue를 가리키지만 blue 앱은 없음" 상태에서 green으로 간다. 정상이다

## 앱 컨테이너 실행 계약

| 항목 | 값 | 근거 |
|---|---|---|
| 이미지 | `IMAGE_REPOSITORY@sha256:<64자>`만. 태그만이면 거절. 받은 뒤 RepoDigests로 다시 확인 | 태그는 다시 쓸 수 있다. 같은 입력이 언제나 같은 이미지 |
| 설정·비밀값 | `SPRING_PROFILES_ACTIVE=prod`, `TZ=UTC`만 넘긴다. 앱이 EC2 역할로 SSM `/homestamp/prod/app/`을 직접 읽는다 | 04 6장. 비밀값을 환경변수로 넘기면 `docker inspect`에 보인다. 컨테이너에서 IMDSv2에 닿도록 EC2 hop limit은 2(`ec2.tf`) |
| Flyway | 앱은 Flyway를 돌리지 않는다(prod 프로필 `spring.flyway.enabled=false`, #173). 스키마는 4단계 `--migrate`만 바꾼다 | 04 6장 |
| 메모리 | `--memory=800m`, 이미지의 `-XX:MaxRAMPercentage=60` | 04 8장 |
| 재시작 | `--restart unless-stopped`. 손으로 멈춘 이전 앱은 재부팅해도 다시 뜨지 않는다 | 04 7장 |
| 격리 | 읽기 전용 루트, `/tmp`만 tmpfs, `--cap-drop ALL`, `no-new-privileges`, 비밀 폴더를 묶지 않음 | |
| 로그 | Docker json-file 10MB×3. 배포 출력에는 앱 로그를 옮기지 않는다(`docker logs homestamp-app-<슬롯>`) | 04 8장 "디스크" |
| 정상 종료 | `docker stop -t 30`(SIGTERM 뒤 30초) | 04 8장 `server.shutdown=graceful` |

Migration·GRANT 컨테이너(`homestamp-app-migrate`, `homestamp-app-grants`)는 같은 이미지를 `--user $MIGRATION_UID`(10002), 읽기 전용 루트, 권한 없음, 프로필·설정 환경변수 없이(`TZ`만) 돌린다. 호스트의 `MIGRATION_SECRETS_DIR`(운영 `/etc/homestamp/migration`)을 컨테이너 안 `/run/secrets/homestamp-migration`에 **읽기 전용으로 묶기만** 한다. `deploy.sh`는 내용을 읽지 않고 모양만 검사한다(아래 "Migration 비밀 폴더", #173 계약: 정확히 4개 파일). 인증서는 비밀 파일 URL의 `sslrootcert=/app/certs/rds-ca.crt`(이미지 안, #207). 웹 앱에는 이 폴더를 묶지 않는다.

- **제한 시간**: 떼어 놓고 돌려 2초마다 보고, `--migrate`는 `MIGRATE_TIMEOUT`(900초), `--apply-grants`는 `GRANTS_TIMEOUT`(300초)을 넘기면 `docker stop -t 30`으로 멈추고 11·12로 끝낸다. **`--apply-grants`를 모르는 이미지(#299 전)는 웹 앱으로 떠 끝나지 않으므로** 이 제한으로 끝난다(새 앱 시작 안 함)
- 멈추지 못하면 그대로 두고 실패로 끝낸다. 다음 배포는 그것이 실행 중인 동안 종료 5로 거절한다(잠금이 풀려도 Migration이 겹치지 않음)
- 끝났음(`exited`)을 확인한 뒤에만 출력의 마지막 100줄(값을 넣지 않는 #173·#299 문장)을 배포 출력에 옮기고 지운다. 상태를 확인하지 못하면 지우지 않고 실패로 끝낸다. 시간 초과로 멈춘 것은 `docker logs`로 보도록 남기고 다음 배포가 지운다
- Migration을 멈추면 그때 돌던 버전의 트랜잭션만 PostgreSQL이 되돌린다(앞 버전은 이미 커밋). GRANT는 한 트랜잭션이라 멈추면 바뀐 권한이 없다

## Migration 비밀 폴더 (`/etc/homestamp/migration`, decisions 2026-11-28)

처음 한 번 만들면 그 뒤 배포와 매일 중지·시작에서 다시 넣지 않는다. `/run`은 메모리라 중지할 때마다 지워지므로 운영은 암호화된 EBS의 `/etc` 아래를 쓴다(`deploy.env`의 `MIGRATION_SECRETS_DIR`).

| 대상 | 소유자 | 권한 |
|---|---|---|
| `/`, `/etc`, `/etc/homestamp` (위 경로 전부) | root | 그룹·남 쓰기 없음, 링크 아님 |
| `/etc/homestamp/migration` | `MIGRATION_UID`(10002) | 0500, 링크 아님, 아래 4개 이름만 |
| `spring.datasource.url`, `spring.datasource.username`, `spring.datasource.password`, `app.migration.owner-role` | 10002 | 0400, 일반 파일, 비어 있지 않음 |

- `deploy.sh`는 Migration 직전에 이 표를 검사한다. 하나라도 다르면 Migration·GRANT·새 앱을 하지 않고 **11**(`failed_step: migrate`)로 멈춘다. 활성 앱과 nginx는 그대로다. 출력에는 어긋난 이름·경로만 나오고 값은 나오지 않는다
- 같은 digest noop·`--status`는 이 폴더를 보지 않는다. 서버가 켜질 때 Migration은 돌지 않는다(Migration 컨테이너는 재시작 정책 없이 한 번 돌고 지워진다)
- 값: URL은 `jdbc:postgresql://<db_endpoint_address>:5432/homestamp?sslmode=verify-full&sslrootcert=/app/certs/rds-ca.crt`, 사용자 `hs_migrator`, Owner `hs_owner`(DB-보관-삭제 "운영 Role Bootstrap"), 비밀번호는 RDS-Bootstrap-접속 "로그인 역할 비밀번호"에서 정한 값
- `deploy.sh`·`deploy.env`는 root 소유·그룹/남 쓰기 막힘이어야 SSM 문서가 실행한다(`deploy-command.sh.tftpl`). 이 폴더를 바꿀 수 있는 사람도 root뿐이다

### 경계와 한계
- **앱(10001)**: 이 폴더를 묶지 않고 Docker 소켓·privileged·호스트 경로도 없다. 묶이더라도 0500·0400이라 읽지 못한다(Linux에서 확인한다. Docker Desktop은 bind mount 권한을 강제하지 않는다)
- **암호화 EBS는 저장 매체 보호다.** 떼어 낸 디스크·스냅숏을 키 없이 읽지 못하게 할 뿐이다. 실행 중인 서버의 root, docker 그룹, `ssm-user`(sudo), 스냅숏·AMI를 복원할 권한이 있는 사람은 읽을 수 있다. 셸은 `homestamp-ops-admin`만 열고(배포 역할은 세션을 못 연다), 셸 입력과 출력은 `logs/ssm/`에 남는다
- **AWS 권한은 나뉘지 않는다.** 앱과 Migration 컨테이너 모두 IMDS로 같은 EC2 역할을 받는다(hop limit 2). 그래서 Migration·Purge 비밀번호를 SSM·Secrets Manager에 두지 않는다. 반대로 Migration 컨테이너도 앱 설정값과 사진 버킷에 닿을 수 있다. 이 노출은 승인된 digest와 일회성 실행만 돌리는 것으로 관리한다. 실행 주체별 역할(별도 자격 증명 공급)은 지금 만들지 않는다
- **스냅숏·AMI**: 필요 없으면 만들지 않는다. 만든 것은 비밀번호를 담고 있으므로 암호화 유지, 공유 금지, 복원할 수 있는 사람을 운영 담당으로 제한한다. 다른 곳에서 복원했거나 공유된 것이 의심되면 `hs_migrator` 비밀번호를 바꾼다(아래 "복구")

### 처음 만들기·교체 (EC2 셸, root)
`homestamp-shell`로 연 세션은 친 명령과 화면 출력이 S3에 남는다. 그래서 값은 **화면에 나오지 않는 `read -rs`로만** 넣는다. `echo`·heredoc·편집기 붙여 넣기·명령 인자·`sudo` 인자로 넣지 않는다. `printf`는 셸 내장이라 프로세스 인자에 나오지 않는다.

블록을 통째로 붙여 넣지 않는다. 붙여 넣은 다음 줄이 입력 버퍼에 남아 `read`가 그 줄을 비밀번호로 읽는다. **세 묶음으로 나눠 차례로 실행하고, 2는 그 한 줄만 따로 실행한다.**

1) 새 폴더 준비(값 없음)
```sh
sudo -i                                    # 이후 root. 아래 줄에는 값이 없다
set +x; umask 077                          # 실행 추적 끔, 새 파일은 처음부터 root 0600
d=/etc/homestamp/migration; n=/etc/homestamp/migration.new
install -d -o root -g root -m 0755 /etc/homestamp
rm -rf "$n" && install -d -o root -g root -m 0700 "$n"
printf '%s' 'jdbc:postgresql://<db_endpoint_address>:5432/homestamp?sslmode=verify-full&sslrootcert=/app/certs/rds-ca.crt' >"$n/spring.datasource.url"
printf '%s' hs_migrator >"$n/spring.datasource.username"
printf '%s' hs_owner >"$n/app.migration.owner-role"
```
2) 비밀번호(이 줄만 실행한 뒤 붙여 넣고 Enter. 화면에 안 나온다)
```sh
IFS= read -rs pw && printf '%s' "$pw" >"$n/spring.datasource.password"; unset pw; echo
```
3) 검사하고 배포 잠금 아래에서 바꿔 끼우기(배포 중이면 잠금을 못 잡아 아무것도 바꾸지 않는다)
```sh
flock -n /run/lock/homestamp-deploy.lock sh -c 'set -e; d=/etc/homestamp/migration; n=$d.new
  [ -s "$n/spring.datasource.password" ]
  chown -R 10002:10002 "$n"; chmod 0400 "$n"/*; chmod 0500 "$n"
  if [ -e "$d" ]; then mv "$d" "$d.old"; fi; mv "$n" "$d"; rm -rf "$d.old"' && echo "교체함" || echo "교체 안 함: 배포 중이거나 비밀번호 파일이 비어 있음"
stat -c '%u %a %n' /etc/homestamp "$d" "$d"/*   # 값이 아니라 소유자·권한만 본다: 0 755, 10002 500, 10002 400 ×4
exit
```
- 잠금 파일은 `deploy.sh` 기본 `LOCK_FILE`과 같아야 한다. `deploy.env`에서 `LOCK_FILE`을 바꿨다면 그 경로를 쓴다
- 1·2에서 끊기거나 실패하면 `migration.new`(root 0700)만 남고 쓰던 폴더는 그대로다. 1부터 다시 하면 지우고 새로 만든다
- 3에서 멈췄을 때: `migration`이 없고 `migration.old`만 있으면 **먼저 `mv /etc/homestamp/migration.old /etc/homestamp/migration`으로 되돌린다**(그것이 유일한 정상 사본). `migration`과 `migration.old`가 둘 다 있으면 교체는 끝난 것이니 `.old`를 지운다
- 비밀번호 파일이 비면 3이 바꾸지 않는다. `deploy.sh`도 빈 파일을 11로 거절한다
- 내용은 `cat`으로 보지 않는다. 확인은 소유자·권한, 다음 배포의 Migration 성공(또는 아래 연결 확인)으로 한다

**처음 한 번은 가짜 값으로 먼저 한다.** 노트북에서 `DUMMY-`로 시작하는 임의 문자열을 만들어 위 절차 전체를 돌린 뒤 세션을 닫는다. 그 세션 기록에 가짜 값이 없는지 본다(가짜 값이므로 화면에 써도 된다):
```sh
aws s3 cp "s3://homestamp-ops/logs/ssm/<세션 ID>.log" - --profile homestamp --region ap-northeast-2 | grep -c 'DUMMY-<만든 값>'   # 0이어야 한다
aws s3 cp "s3://homestamp-ops/logs/ssm/<세션 ID>.log" - --profile homestamp --region ap-northeast-2 | grep -c 'read -rs'          # 1 이상(기록이 실제로 남음)
```
0이 아니면 진짜 값을 넣지 않고 멈춘다. 가짜 폴더는 진짜 절차가 그대로 덮어쓴다. 기록 파일의 실제 이름·위치는 처음 실행 때 확인해 이 문서를 고친다.

### 연결 확인 (값 없이, 배포와 겹치지 않게)
배포 잠금을 잡고 지금 활성 이미지로 `--migrate`를 한 번 돌린다. 이미 적용된 이력이면 바꾸는 것 없이 0으로 끝난다(통합 시험 B2):
```sh
sudo /opt/homestamp/deploy/deploy.sh --status                          # active 슬롯 확인
img="$(sudo docker inspect -f '{{.Config.Image}}' homestamp-app-<활성 슬롯>)"
sudo flock -n /run/lock/homestamp-deploy.lock docker run --rm --pull never --user 10002:10002 --read-only --memory 800m \
  --tmpfs /tmp:rw,nosuid,nodev,size=64m --cap-drop ALL --security-opt no-new-privileges -e TZ=UTC \
  --mount type=bind,src=/etc/homestamp/migration,dst=/run/secrets/homestamp-migration,readonly "$img" --migrate; echo "rc=$?"
```
- 0: 접속·인증 성공. 1: 출력 문장(값 없음)으로 원인을 본다. 잠금을 못 잡으면 배포 중이니 나중에 한다
- 활성 이미지가 DB 이력보다 오래되면(손으로 되돌린 뒤) 실패할 수 있다. 그때는 다음 배포로 확인한다. 첫 배포 전에는 첫 배포가 이 확인이다

### 복구
| 상황 | 할 일 |
|---|---|
| 파일 누락·권한 틀림(배포 11) | 위 "처음 만들기·교체"를 다시 한다. 비밀번호를 모르면 아래 줄 |
| `hs_migrator` 비밀번호 교체·분실 | RDS-Bootstrap-접속 "로그인 역할 비밀번호"로 새 값을 DB에 정한 뒤 이 절차로 파일을 다시 만든다. 그사이 배포는 11로 멈추고 서비스는 그대로다 |
| EC2 교체·EBS 유실 | 새 EC2에 설치를 마친 뒤 위와 같이 새 비밀번호를 정하고 파일을 만든다. 따로 보관한 사본은 없다(Migration 비밀번호는 데이터를 지키는 키가 아니라 다시 정하면 된다). 앱 설정값은 SSM에 있어 그대로다 |
| 개인 계정에 새 환경 | 옮기지 않는다. 새 계정에서 Bootstrap을 하고 모든 비밀번호·키를 새로 만든다(04 13-4) |

## 헬스 체크

- 새 슬롯의 `http://127.0.0.1:<8081|8082>/actuator/health`가 **200이고 본문에 `"status":"UP"`**일 때만 통과. 3초 제한으로 3초마다, 최대 `HEALTH_TIMEOUT`(120초)
- 이 경로는 앱에 실제로 있다(Actuator 기본 노출, SecurityConfig가 허용). 전체 상태에 **DB 지표가 들어 있어 DB에 닿지 못하면 DOWN·503**이라 통과하지 못한다. SSM 값이 모자라 앱이 뜨지 않으면 컨테이너가 멈추고 바로 실패(종료 13)
- 바깥에서는 nginx가 `/actuator`를 404로 막는다(#204). 헬스 체크는 nginx를 거치지 않고 앱 포트로 직접 한다
- readiness 그룹(`/actuator/health/readiness`)은 있지만(200) **DB를 넣지 않아** DB를 멈춰도 UP이다(#207 확인). 그래서 DB가 들어 있는 `/actuator/health`를 쓴다
- 한계: 헬스는 앱·DB 연결까지만 본다. 실제 요청 처리는 전환 뒤 확인(nginx 경유 401)이 본다

## 전환 뒤 확인과 되돌리기

- 전환이 성공하면 upstream 파일이 새 슬롯인지 보고, `POST_SWITCH_URL`(`https://homestamp.cloud/api/`, `--resolve`로 이 서버의 nginx)에 요청한다. **응답이 정확히 `POST_SWITCH_EXPECT`(401)이고, nginx가 붙인 `X-Homestamp-Upstream`이 정확히 한 줄로 그 슬롯 주소(`127.0.0.1:<포트>`)일 때만 통과**: 인증 없는 `/api/`는 앱(Spring Security)만 401을 준다. nginx 자신의 404(location·host 불일치)·503(`@api_unavailable`)·연결 실패, 이전 슬롯의 401, 헤더 없음·여러 줄·다른 주소는 실패. 매번 새 연결로 `VERIFY_TIMEOUT`(20초) 안에서 1초 간격으로 다시 묻는다
- 슬롯 식별: nginx는 이 서버 자신(127.0.0.1)에서 온 요청에만 `X-Homestamp-Upstream: $upstream_addr`(실제로 답한 앱 주소)를 붙이고, 앱이 같은 이름을 보내면 지운다(`nginx.conf` map, `snippets/proxy-api.conf`). 밖의 요청에는 나가지 않는다(값이 비면 보내지 않음, `real_ip`를 쓰지 않아 주소를 꾸밀 수 없음). 그래서 확인 요청은 127.0.0.1로 가야 한다: `POST_SWITCH_RESOLVE`는 `<URL의 이름>:<URL의 포트>:127.0.0.1`만 받고, 비어 있으면 `POST_SWITCH_URL`이 127.0.0.1이어야 한다. 아니면 매 배포가 16으로 끝나므로 처음부터 2로 거절한다
- reload 기다림: `nginx -s reload`는 신호만 보내고 돌아오고, 이전 작업 프로세스는 처리 중인 요청을 마칠 때까지 옛 주소로 답한다(통합 시험에서 이 사이의 이전 앱 401을 새 슬롯 성공으로 본 오판을 찾음). `switch-upstream.sh`는 reload 전 작업 프로세스 PID를 적어 두고 모두 끝난 뒤에 0으로 끝난다(`RELOAD_WAIT` 45초, 넘으면 되돌리고 1). nginx `worker_shutdown_timeout 30s`가 그 끝을 정한다. 이전 앱은 그 뒤 전환 뒤 확인이 통과해야 멈추므로, 처리 중이던 요청이 이전 앱에서 끝난다
- 실패하면 이전 앱이 실행 중일 때 `switch-upstream.sh`로 이전 슬롯으로 되돌리고, **이전 앱이 nginx를 거쳐 다시 401을 주고 답한 앱이 이전 슬롯일 때만**(같은 식별) 되돌린 것으로 보고 새 앱을 멈춘다(종료 16, `rolled_back:true`). `switch-upstream.sh`의 종료 코드만으로 되돌렸다고 보지 않는다
- 되돌리기를 확인하지 못하면(전환 실패·이전 앱 무응답) 두 앱을 모두 남기고 종료 17(`rolled_back:false`). 어느 쪽도 멈추지 않는다. 처음 배포(이전 앱 없음)에서 확인이 실패하면 새 앱을 그대로 두고 16
- **되돌려도 DB는 그대로다.** 전환과 되돌리기 사이(수 초) 새 앱이 받은 요청의 쓰기, 그리고 4·5단계의 Migration·GRANT는 남는다. 그래서 스키마는 언제나 이전 앱과도 맞게 쓴다(04 8장 "스키마 변경": 추가 먼저, 삭제는 다음 배포). 지우는 Migration이 있는 배포 전에는 RDS 수동 스냅숏(04 8장)

## 잠금과 다시 실행

- `flock -n /run/lock/homestamp-deploy.lock`으로 배포 전체(잠금 획득부터 기록까지)를 하나만 돌린다. 기다리지 않고 거절한다(CD가 다시 실행). GitHub Actions의 `concurrency`와 별개로 서버에서 한 번 더 막는다
- 잠금은 프로세스가 끝나면(강제 종료 포함) 커널이 푼다. `/run`은 재부팅하면 비므로 잠금 파일도 사라진다
- 강제 종료(`kill -9`, SSM 시간 초과)되면 `in-progress.json`이 남는다. 다음 실행이 이것을 `interrupted`로 기록에 옮긴다. 그때 떠 있던 Migration 컨테이너는 계속 돈다 → 다음 실행은 그것이 끝날 때까지 종료 5(Migration을 중간에 죽이지 않는다)
- 신호(SIGTERM·INT·HUP): 2초 단위로 기다리는 중이라 바로 멈추고 129·130·143으로 `interrupted`를 남긴다. 그때 돌던 Migration·GRANT 컨테이너는 계속 돌고 다음 배포는 끝날 때까지 종료 5. 전환 중이었다면 upstream 파일이 가리키는 쪽이 활성이다(`--status`)
- **잠금이 보호하는 범위**: 잠금 획득부터 활성 판단, 이미지, Migration, GRANT, 새 앱, 전환, 되돌리기, 기록까지 한 프로세스 안이다. 서버 밖 DB 잠금은 아니다(#299의 GRANT advisory lock은 GRANT끼리만)
- **손으로 Migration·GRANT를 돌릴 때도 같은 잠금 안에서 한다**: `sudo flock -n /run/lock/homestamp-deploy.lock docker run ... --migrate`(아래 "손으로 되돌리기"처럼). 운영 DB에 바로 붙는 다른 곳(관리자 노트북·#203 접속)에서는 Migration·GRANT를 돌리지 않는다. 분산 잠금은 두지 않는다(단일 EC2)
- 다시 실행은 언제나 안전하다: 활성은 upstream 파일로 다시 읽고, 비활성 슬롯의 컨테이너(멈춘 이전 앱, 실패해 남긴 앱)는 지우고 새로 만든다. 활성 슬롯 컨테이너는 지우지 않는다

## 재부팅 뒤

- nginx(`restart: unless-stopped`)와 활성 앱(`unless-stopped`)은 Docker가 다시 띄운다. 손으로 멈춘 이전 앱은 뜨지 않는다. upstream 파일은 디스크에 남아 같은 슬롯을 가리킨다
- 확인: `sudo /opt/homestamp/deploy/deploy.sh --status` → `active:`와 각 슬롯 상태, 마지막 기록
- 아침에 RDS가 늦게 켜지면 활성 앱의 헬스가 잠시 DOWN일 수 있다(앱이 DB 연결을 재시도, 04 7장). 이것은 배포 실패가 아니다
- 켜질 때 Migration은 돌지 않는다. Migration 비밀 폴더(`/etc/homestamp/migration`)와 앱 설정값(SSM)은 그대로 남아 다음 배포에 다시 넣을 것이 없다
- 재시작 정책은 컨테이너가 죽었을 때 다시 띄울 뿐이다. 앱이 떠 있지만 DB·SSM에 닿지 못하는 상태가 오래가면 `--status`·헬스로 보고 원인을 고친다(실환경 확인 7)

## 손으로 되돌리기 (종료 17, 또는 배포가 끝난 뒤 문제를 발견했을 때)

```sh
sudo flock -n /run/lock/homestamp-deploy.lock bash         # 잠금을 쥔 셸(실패하면 배포 중). 아래는 이 셸 안에서
sudo /opt/homestamp/deploy/deploy.sh --status               # active와 이전 슬롯 확인
docker start homestamp-app-<이전>                           # 멈춰 둔 이전 앱(지우지 않고 남아 있음)
curl -fsS http://127.0.0.1:<이전 포트>/actuator/health      # {"status":"UP"} 될 때까지
sudo /opt/homestamp/nginx/switch-upstream.sh 127.0.0.1:<이전 포트>
docker stop -t 30 homestamp-app-<지금>
```
- 이전 앱이 지금 스키마에서 도는지는 "스키마는 이전 앱과도 맞게" 규칙에 달렸다. 지우는 Migration 뒤라면 되돌리지 말고 고친 이미지로 앞으로 배포한다
- 되돌린 일은 대장에 적는다(`history.jsonl`에는 남지 않는다)

## upstream을 모름 (종료 4)

`cat /opt/homestamp/nginx/run/upstream/upstream.conf`. 손으로 고쳤거나 다른 주소면, 실제로 응답하는 슬롯을 헬스로 확인한 뒤 `switch-upstream.sh 127.0.0.1:<그 포트>`로 바로잡고 다시 배포한다.

## 같은 이미지인데 확인 실패 (종료 4, `noop-check`)

같은 digest가 활성 슬롯에서 돌고 있어도 noop으로 끝내기 전에 그 슬롯의 `/actuator/health`(UP)와 전환 뒤 확인(401 + `X-Homestamp-Upstream`이 그 슬롯)을 본다. 전환한 뒤 확인하기 전에 배포가 멈췄으면(SSM 제한 시간 뒤 강제 종료·재시작) upstream은 확인한 적 없는 슬롯일 수 있기 때문이다.

- **통과**: noop(0). 다른 슬롯 앱이 아직 떠 있으면 멈춘 배포가 9단계(이전 앱 멈춤)를 못 한 것이라 그것만 한다(지우지 않음)
- **실패**: noop으로 보지 않고 아무것도 바꾸지 않은 채 4. 다시 같은 digest로 배포해도 같다. `deploy.sh --status`·`docker ps`로 두 슬롯을 보고, 헬스와 nginx 경유 응답이 맞는 슬롯으로 "손으로 되돌리기"처럼 `switch-upstream.sh`를 부른 뒤 그 슬롯의 이미지가 아닌 앱을 멈춘다. 그 뒤 원하는 digest로 다시 배포한다

## DB 호환성 (블루/그린 동안)

Migration·GRANT는 **blue가 요청을 받는 동안** 돌고, 실패해도 DB를 되돌리지 않는다(앱 롤백 ≠ DB 롤백). 그래서:
- **Expand–Contract**: 한 배포의 Migration은 이전 앱이 그대로 돌 수 있는 것만(테이블·컬럼·인덱스 추가, NULL 허용 또는 기본값 있는 컬럼). 지우기·이름 바꾸기·NOT NULL 조이기·타입 바꾸기는 새 앱이 더 이상 옛 것을 쓰지 않는 **다음 배포**에서
- 권한도 같다: GRANT 정책에서 **회수**는 이전 앱이 그 권한을 안 쓴다는 것을 확인한 다음 배포에서(#299 런북 "남은 위험")
- Migration은 성공하고 새 앱이 실패하면(13·14·15·16) blue가 새 스키마로 계속 돈다. 위 규칙이 이것을 안전하게 만든다
- 이 규칙을 깨는 Migration·권한 회수는 **배포 전 리뷰 대상**이다(PR에 표시, 지우는 Migration 전 RDS 수동 스냅숏, 04 8장)

## 백그라운드 작업 (blue와 green이 겹칠 때)

헬스 체크부터 이전 앱을 멈출 때까지(수십 초~2분) 두 앱의 예약 작업이 함께 돈다. 지금 코드(2026-11-27 dev)에서 확인한 것:
- `OutboxPoller`(문자 아웃박스): `FOR UPDATE SKIP LOCKED`로 줄을 잠가 `SENDING`으로 바꾸고 커밋한 뒤 보낸다 → 두 앱이 같은 줄을 가져가지 않는다. 보내는 중 멈추면 `SENDING`으로 남고 다시 보내지 않고 전달 조회로 맞춘다
- `DeliveryPollScheduler`(전달 결과 조회, `app.delivery.poller.enabled=true`일 때만): `SKIP LOCKED` + 유한 보호(`protect-for`)
- 그래서 **두 앱이 겹쳐도 중복 발송·중복 처리는 없다**. 이 스크립트는 green의 예약 작업을 끄지 않는다(끄면 전환 뒤 켜는 단계가 필요해진다)
- 새 예약 작업(기다림 타이머 등)을 더할 때는 같은 규칙(`SKIP LOCKED` 또는 상태 조건부 갱신)을 지켜야 한다. 지키지 못하면 이 스크립트가 아니라 그 PR에서 막는다

## 자원 (t3.small 2GB + 스왑 4GB, 04 8장)

- 겹치는 순간: blue(`--memory 800m`) + Migration(800m) → blue + green(800m×2) + nginx. 이미지의 `-XX:MaxRAMPercentage=60`이라 힙은 컨테이너마다 약 480MB. 스왑을 쓸 수 있다
- DB 연결: 앱마다 Hikari 기본 10개 → 겹칠 때 약 20개 + Migration. db.t4g.micro의 `max_connections`(약 80~100) 안
- 이미지 받기 실패(디스크 부족 포함)는 종료 10, 이전 앱 그대로. 오래된 이미지 정리는 아직 없다(04 8장 "디스크")
- **실제 메모리·스왑·기동 시간은 측정하지 않았다**: 첫 배포 뒤 04 8장 "medium으로 키우는 기준"대로 잰다

## 화면(React)

이 스크립트는 백엔드만 배포한다. 화면은 따로 발행한 정적 파일 이미지를 `deploy-front.sh`가 `/srv/homestamp/front`에 설치하고 `current` 링크만 바꾼다(nginx reload 없음). 절차·종료 코드·복구는 `docs/runbooks/배포-화면.md`.
- 같이 쓰는 것은 잠금 파일(`/run/lock/homestamp-deploy.lock`) 하나다. 화면 배포 중이면 이 스크립트는 3으로 끝난다(그 반대도). 상태 폴더는 따로(`/var/lib/homestamp/deploy-front`)
- 이 스크립트는 화면 파일·`current` 링크를 건드리지 않는다. 백엔드를 되돌려도 화면은 그대로다
- **호환**: 두 판이 따로 바뀌므로 API는 Expand–Contract(백엔드가 필드를 먼저 더하고 → 화면 → 다음 배포에서 옛 필드 제거). 순서는 배포-화면.md "백엔드와 함께 바뀔 때"

## 통합 시험 (실제 nginx·이미지·PostgreSQL, 로컬)

```sh
docker build -t homestamp-int-real:local back      # 시험할 백엔드 이미지(운영 발행본이 아님)
infra/deploy/test/integration-test.sh . "$(mktemp -d)" homestamp-int-real:local
```
host 네트워크의 80·443·15100·18181·18182를 쓰고 `homestamp-nginx` 컨테이너가 있으면 멈춘다(지우지 않음). CI에서는 돌리지 않는다. `infra/`·`back/Dockerfile`·Migration 실행 방식이 바뀌면 돌린다. 이미지 안의 앱 코드는 그때 빌드한 것이므로, 결과는 그 커밋의 이미지에만 해당한다(운영 digest는 실환경 확인에서 따로 본다).

- 2026-11-27 결과(63개 통과, AWS 없음):
  - 실제 nginx(#204 설정·`render.sh`·`switch-upstream.sh`, HTTPS는 시험 CA, host 네트워크) + 가짜 앱: 첫 배포·Blue→Green·되돌림(404·503 → 16, 같은 식별)·처리 중 요청이 있는 reload(요청이 끊기지 않고 끝난 뒤 전환 완료)·기다림 제한 초과(15, 되돌림)·되돌리기 확인 실패(17, 두 컨테이너 남김)·nginx 꺼짐(15)·모르는 upstream(4)·noop, 밖의 요청에 확인 헤더 없음·보안 헤더·Cache-Control·HSTS 정책 그대로
  - 실제 이미지(`back/Dockerfile` 빌드 위에 시험 CA 파일 하나만 더함, 앱 jar 같음) + PostgreSQL 18.6(`bootstrap_roles.sql`): `--migrate`·`--apply-grants`가 verify-full TLS로 적용되고 다시 실행해도 같음, DB가 꺼져 있으면 11(GRANT·새 앱 없음), 출력·기록에 비밀번호·JDBC 주소 없음
  - **하지 못한 것**: 실제 앱의 웹 시작·헬스·전환. prod 프로필은 SSM Parameter Store가 있어야 떠서 로컬에서는 시작 단계에서 멈춘다(13, `AWS 리전을 확인할 수 없다`). 두 앱이 함께 뜬 동안의 Poller 동시 실행도 같은 이유로 실제로 돌려 보지 못했다(코드상 `SKIP LOCKED`). 운영 EC2에서 첫 배포(noop부터)로 확인한다

## 실환경 첫 배포 전 필수 확인 (로컬에서 못 본 것)

로컬 시험으로는 아래를 볼 수 없다. 첫 사용자 공개 전에 이 순서로 확인한다. 같은 digest 재배포(noop) 성공만으로 블루/그린을 확인했다고 보지 않는다.

1. 첫 운영 백엔드 시작: SSM 설정 조회, prod 프로필 웹 시작, RDS verify-full TLS 연결, 헬스(DB readiness)
2. 같은 digest 재배포: noop과 CD 경로(#206) 전체
3. 기능상 안전한 새 digest로 실제 Blue→Green 전환(전환 뒤 확인의 `X-Homestamp-Upstream`·reload 기다림 포함)
4. 두 앱이 겹친 동안 Poller(`SKIP LOCKED`) 중복 처리 없음
5. EC2 메모리·스왑과 DB 커넥션 수(두 앱 동시)
6. 통제된 실패(예: 시작 실패 이미지)로 되돌리기와 복구
7. 재부팅 뒤 nginx·앱 자동 시작과 `--status`
8. 화면 독립 배포(배포-화면.md "실환경에서 확인할 것") 뒤 사용자 공개

9. Migration 비밀 폴더: 가짜 값으로 만든 세션 기록에 값이 없음, 앱 UID 10001이 파일을 못 읽음. 내용은 어디에도 내지 않고 컨테이너 안 읽기 결과의 종료 코드만 본다: `sudo docker run --rm --entrypoint sh --user <UID> -v /etc/homestamp/migration:/s:ro <앱 이미지> -c 'cat /s/spring.datasource.password >/dev/null 2>&1'; echo "rc=$?"`를 `10002:10002`(대조군, rc=0)와 `10001:10001`(rc≠0)로 돌린다. 대조군이 0이 아니면 명령 자체가 잘못된 것이니 판단하지 않는다. 출력을 컨테이너 안에서 버리므로 10001이 뜻밖에 읽어도 값이 화면·세션 기록·컨테이너 로그에 남지 않는다. 이미지 ENTRYPOINT가 java라 `--entrypoint`가 필요하다, 권한을 하나 틀리게 한 배포가 11로 멈추고 활성 앱 그대로
10. 비밀값을 다시 넣지 않은 두 번째 배포, EC2·RDS 중지·시작 뒤 새 digest 배포

- **정한 것**: Migration 비밀 폴더 `/etc/homestamp/migration`, `MIGRATION_UID=10002:10002`(위 "Migration 비밀 폴더", decisions 2026-11-28)
- **정할 것**: GHCR 저장소 이름
- **관리 포트**: 앱에 `management.server.port`가 아직 없어 이 스크립트는 9091·9092를 다루지 않는다(04 11장에도 적음). 앱에 생기면 사설 IP에 묶는 방법과 함께 넣는다(후속)

# 화면(React) 배포 — `deploy-front.sh`

백엔드 블루/그린(`배포-블루그린.md`)과 따로 화면 정적 파일만 바꾼다. 같은 EC2·같은 nginx를 쓰고, 같이 쓰는 것은 잠금 파일(`/run/lock/homestamp-deploy.lock`) 하나다.
이미지 발행 계약은 `이미지-발행.md`(화면), CD 실행은 `배포-자동화.md`(`component=front`), nginx 자리는 `HTTPS-nginx.md` 7장.

## 하는 것과 하지 않는 것

- **한다**: 화면 이미지(`FROM scratch`, `/site`만)를 digest로 받아 확인 → 실행하지 않는 컨테이너에서 파일만 꺼내 검사 → 공용 assets·릴리스 설치 → `current` 링크를 한 번에 바꿈 → HTTPS로 실제 응답 확인(실패하면 이전으로 되돌리고 다시 확인)
- **하지 않는다**: 백엔드 빌드·재시작, Migration·GRANT, 블루/그린 전환, nginx 설정 변경·reload, Migration 비밀 폴더 접근, 이미지 실행(`docker run`)
- 자동 재시도·자동 재전송은 없다. 실패하면 원인을 보고 사람이 다시 실행한다

## 자리

```
/srv/homestamp/front/            FRONT_ROOT (nginx가 읽기 전용으로 묶음)
  releases/<배포 ID>/            index.html·version.json·public 파일(해시 없는 파일). 설치 뒤 바꾸지 않음
  assets/                        Vite 해시 이름 파일의 공용 폴더(모든 릴리스가 같이 씀)
  current -> releases/<배포 ID>  nginx root. mv -T로 한 번에 바꿈(reload 없음)
  .incoming/                     꺼낸 파일 검사 자리(root 0700). 검사 전 파일은 releases·assets에 두지 않음
/var/lib/homestamp/deploy-front/ STATE_DIR (백엔드 /var/lib/homestamp/deploy와 따로. 같으면 종료 2)
  in-progress  last-good  releases.log  commits  manifests/<ID>.manifest  history.jsonl  last.json
/opt/homestamp/deploy/deploy-front.sh   (root 0755, 해시를 SSM 문서에 고정)
/opt/homestamp/deploy/deploy-front.env  (root, 그룹·남 쓰기 없음. 예시 infra/deploy/deploy-front.env.example)
```

- **배포 ID**: `<UTC 시각>-<번호>`(예 `20261127T061625Z-1`). 같은 이미지를 다시 배포해도 새 ID·새 폴더(예전 폴더를 다시 쓰지 않음)
- **manifest**: 커밋·digest·설치 시각·assets 목록(sha256 이름)·릴리스 파일 목록(sha256 경로). 확인·정리의 기준
- **commits**: `<커밋> <digest>`. 같은 커밋에 다른 digest가 오면 23(릴리스를 지운 뒤에도)

## nginx (HTTPS-nginx.md 7장)

- `/` → `current`(SPA는 `index.html`로, `no-cache`)
- `/assets/` → 공용 `assets/`(해시 이름이라 200·304만 긴 캐시. 없으면 404에 `no-store`). 릴리스 폴더 안의 `assets`는 보지 않는다
- `= /version.json` → `current/version.json`, `no-store`(없으면 404). 배포 확인이 이것으로 지금 나가는 커밋을 본다
- `/api/`는 그대로. 화면 배포는 nginx를 reload하지 않는다(`open_file_cache` 없음 → 링크를 바꾸면 다음 요청부터 새 판)

## 파일 계약 (CI `check-front.sh`와 서버 `deploy-front.sh`가 같은 규칙)

- 이미지: digest로 받기, RepoDigests가 같은 digest, `linux/amd64`, 레이어 하나, 라벨 `org.opencontainers.image.revision` = 40자 커밋, `/site` 밖 파일 없음
- 파일: 일반 파일·폴더만(링크·하드링크·특수 파일 거절), 이름은 `[A-Za-z0-9._-]`이고 점으로 시작하지 않음, 소스맵·`node_modules`·`.ts(x)`·`package*.json` 없음, 허용 확장자만, `index.html` 있음, `version.json` = `{"revision":"<커밋>"}` 그대로
- `assets/`: 하위 폴더 없음, `<이름>-<8자>.<확장자>`만. `index.html`이 `/assets/`의 JS·CSS를 부르고 그 파일이 있음
- 한도: 파일 2000개, 파일 하나 10 MiB, 전체 50 MiB(넘으면 24). 2026-11-27 실제 빌드는 96개·약 4 MB·가장 큰 파일 755 KB
- 디스크: 꺼내기 전에 `FRONT_ROOT` 파일시스템에 `MIN_FREE_BYTES`(1 GiB) + 이미지 크기×2가 남아야 한다(아니면 24, 아무것도 안 바꿈)
- 설치한 파일은 새로 만들어 `0644 root`(이미지의 권한·소유자를 믿지 않음)
- 두 검사가 같은 판단을 하는지: `infra/deploy/test/front-test.sh` F12(같은 이미지를 둘에 넣음). 서버 스크립트는 다른 스크립트를 불러오지 않는다(해시 경계)

## 순서

1. 잠금(백엔드 배포 중이면 3) → 지난 실행의 임시 파일 정리
2. 끝나지 않은 배포(`in-progress`)가 있으면 실제 응답으로 판단해 마무리(전환 뒤 멈춘 배포를 성공으로 마무리할 때도 일반 배포와 같이 새 판과 이전 판의 assets를 모두 확인). 판단할 수 없으면 **어떤 digest든** 4로 멈춤
3. `current`가 `last-good` 릴리스(manifest 정상)인지. 아니면 4. 기록이 없으면 `current`가 없거나 손으로 둔 링크여야 함(첫 배포)
4. 이미지 받기·확인(10·24) → 커밋↔digest(23)
5. 같은 digest가 이미 `last-good`이면 HTTPS 확인을 통과할 때만 noop(0), 통과하지 못하면 4
6. 지금 나가는 상태(되돌릴 대상)를 HTTPS로 확인(precheck). 통과하지 못하면 4(아무것도 안 바꿈)
7. 디스크 확인 → `in-progress`(prepare) → 꺼내기·검사(22·24) → assets 충돌 확인(23, 덮어쓰지 않음) → assets 설치 → 릴리스 설치 → manifest
8. `in-progress`(switched, 이전 대상 기록) → `current` 전환(15)
9. HTTPS 확인(`VERIFY_TIMEOUT` 동안 다시 물음): TLS 검증 유지,
   - `version.json` 200·JSON·`no-store`·내용 그대로
   - `/` 200·`text/html`·manifest의 `index.html` sha256
   - manifest의 모든 assets(동적 chunk 포함) 200·MIME·sha256, 없는 assets 이름은 404
   - 이전 릴리스의 assets도 그대로(열린 브라우저)
10. 성공 → `releases.log` → `last-good`(**배포 확정 지점**) → 정리(GC) → `history.jsonl`·`last.json` → `in-progress` 삭제. 실패 → `in-progress`(rollback) → 이전 `current`로 → 이전 상태를 같은 방식으로 확인(16 또는 17)

## 보존·정리

- 남기는 릴리스 폴더: 최근 정상 3개(`KEEP_RELEASES`) + 이번 + 직전(되돌리기 대상). 그 밖의 ID 모양 폴더만 지운다(모르는 이름은 경고만)
- 남기는 manifest: 위 + 되돌린(사용자에게 잠깐 나갔던) 릴리스 최근 2개(`KEEP_EXPOSED`). 그 assets도 남긴다(새 index를 받은 브라우저)
- assets는 남기는 manifest들의 assets **합집합**만 남긴다(참조 수 세지 않음). 남길 manifest가 하나라도 없거나 손상되면 assets를 지우지 않는다(`gc=skipped`, 경고)
- 정리는 성공한 배포 끝에만 한다. 용량 기준: 릴리스 하나 50 MiB 이하 × 최대 7개 manifest 분량 → 수백 MB 이하(EC2 루트 20 GB)

## 복구

### 상태를 확정할 수 없음 (4)

다음 배포는 이 상태가 풀릴 때까지 **어떤 digest든** 멈춘다. 경우별로:
- **끝나지 않은 배포가 있고 확인 실패**: `--status`의 `in-progress`와 `current`를 본다. 원인(권한·nginx·디스크)을 고치면 다음 실행이 실제 응답으로 확인해 스스로 마무리한다(전환 전이면 interrupted, 전환 뒤 새 판이 나가면 success, 이전 판이 나가면 interrupted+exposed)
- **`in-progress`가 손상됨**: `current`가 `releases/<last-good>`이고 `curl …/version.json`이 last-good 커밋인지 손으로 확인한 뒤에만 `mv in-progress in-progress.broken-<날짜>`로 치운다. 확인되지 않으면 아래 "손으로 되돌리기"
- **`current`가 `last-good`과 다름 / last-good manifest가 없음**: 누가 손으로 바꿨는지 본다. 기록된 판으로 돌리려면 "손으로 되돌리기". manifest를 잃었으면 그 릴리스로는 확인할 수 없으니 다른 정상 릴리스로 돌리고 `last-good`을 그 ID로 고친다(기록을 남긴다)

### 같은 이미지인데 확인 실패 (noop-check → 4)

같은 digest가 이미 정상 릴리스인데 HTTPS 응답이 다르다(파일 권한·nginx·인증서). 아무것도 바꾸지 않았다. 원인을 고치고 같은 digest로 다시 실행하면 noop(0)이 된다. 새 판을 배포해서 덮지 않는다.

### 화면 되돌리기 실패 (17)

링크는 이전 판으로 돌렸지만 이전 판의 응답도 확인하지 못했다(사용자에게 화면이 깨졌을 수 있음). `in-progress`(phase=rollback)를 남긴다.
1. `curl -sSI https://homestamp.cloud/` · `/version.json` · `/assets/<…>`로 무엇이 깨졌는지 본다(nginx 꺼짐·권한·인증서)
2. 원인을 고친다. 고친 뒤 다음 배포가 이전 판을 다시 확인하고 통과하면 마무리하고 진행한다
3. 이전 판도 안 되면 "손으로 되돌리기"로 그 전 정상 릴리스로

### 손으로 되돌리기

```sh
cd /srv/homestamp/front
ls releases/                                   # 남은 릴리스
sudo grep -E '^(commit|digest) ' /var/lib/homestamp/deploy-front/manifests/<ID>.manifest
sudo ln -sfn releases/<ID> .current.tmp.manual && sudo mv -T .current.tmp.manual current
curl -sS https://homestamp.cloud/version.json  # 그 커밋인지
echo <ID> | sudo tee /var/lib/homestamp/deploy-front/last-good   # 확인한 뒤에만
```
`in-progress`가 남아 있으면 위 확인 뒤 `in-progress.manual-<날짜>`로 옮긴다. 한 일은 이슈에 남긴다.

### 지금 상태 확인 실패 (precheck → 4) · 이전 판 assets 손상

전환하기 전에 지금 나가는 판(되돌릴 대상)을 HTTPS로 확인한다(`version.json`·`index.html`·그 판의 모든 assets). 이미 깨져 있으면 전환해도 되돌린 상태를 확인할 수 없으므로 **아무것도 바꾸지 않고 4**(`failed_step=precheck`). 전환한 뒤에 깨지면 되돌린 상태 확인이 실패해 **17**이고 복구 성공으로 기록하지 않는다(`rolled_back=unverified`). 어느 쪽이든 새 판으로 덮어 고치지 않는다(fail-closed). 공용 assets 손상이면:
1. 기록의 실패 문장과 `curl -sS -o /dev/null -w '%{http_code}' https://homestamp.cloud/assets/<이름>`으로 어느 파일인지 본다
2. 그 판의 manifest(`manifests/<ID>.manifest`의 `asset <sha256> <이름>`)와 같은 내용을 그 판 이미지에서 꺼낸다: `docker create --network none <저장소>@<manifest의 digest>` → `docker cp <id>:/site/assets/<이름> /tmp/` → `docker rm` → `sha256sum`이 manifest와 같은지
3. 같을 때만 `install -o root -g root -m 0644 /tmp/<이름> /srv/homestamp/front/assets/<이름>`. 이름은 같은데 내용이 다른 파일이 있으면 지우지 말고 옮겨 두고 이슈에 남긴다(불변 assets를 다른 내용으로 덮어쓰지 않음)
4. 같은 digest로 실행해 noop(확인 통과)인지 본 뒤 새 판을 배포한다

### 충돌 (23)

- **같은 assets 이름, 다른 내용**: 해시 이름이 같은데 내용이 다르면 빌드가 결정적이지 않거나 파일이 바뀐 것이다. 덮어쓰지 않는다. 공용 파일을 손으로 바꾸지 말고 원인(빌드 설정·서버 파일 변조)을 본다
- **같은 커밋, 다른 digest**: 같은 커밋을 다시 발행한 것이다(`sha-<커밋>` 태그를 덮어쓰지 않는 발행 계약 위반). 이미 설치한 digest를 쓰거나 새 커밋으로 발행한다

### 중단 (신호·시간 제한)

- TERM·INT(SSM 시간 제한·취소 포함): 전환 전이면 바뀐 것 없음. 전환 뒤면 이전 판으로 링크를 돌리고 `in-progress`(rollback)를 남긴다 → 다음 실행이 확인
- **확정 지점(`last-good`이 새 판)**:
  - 확정 전에 실패하면 이전 판으로 돌린다. 신호든 기록 쓰기 실패든 같다.
  - 확정 뒤 정리·기록 중에 실패하거나 신호를 받으면 되돌리지 않는다. `current`와 `last-good`은 둘 다 새 판으로 남고, 종료 코드는 실패(143 등)로 남긴다. `in-progress`는 지운다.
  - 정리(GC)는 보존 목록(최근 정상 3개, 이번 판, 직전 판, 되돌린 판의 manifest 2개) 밖만 지운다. 그래서 정리 중에 멈춰도 정상 릴리스와 되돌릴 대상은 남는다.
  - `history.jsonl`·`last.json`은 판단에 쓰지 않는 보고용이다.
- SIGKILL·전원·호스트 장애는 trap으로 막지 못한다. `in-progress`의 phase와 실제 응답으로 다음 실행이 판단하고, 판단할 수 없으면 4
- 문서 실행 제한 600초(받기 몇 MB + 지금 상태 확인 20초 + 꺼내기·검사 + 확인 20초 + 되돌린 뒤 확인 20초 + 정리). CD 기다림 900초

## 첫 설치 (EC2, 사람이 한 번)

1. `sudo install -o root -g root -m 0755 infra/deploy/deploy-front.sh /opt/homestamp/deploy/deploy-front.sh`
2. `deploy-front.env.example` → `/opt/homestamp/deploy/deploy-front.env`(root 0644 또는 0640). `IMAGE_REPOSITORY`는 화면 저장소(백엔드와 다름)
3. `sudo install -d -m 0755 /srv/homestamp/front/releases /srv/homestamp/front/assets` (nginx compose가 `/srv/homestamp/front`를 읽기 전용으로 묶음)
4. **nginx 설정 갱신**: 이 PR의 `infra/nginx/`를 `/opt/homestamp/nginx/`에 반영 → `render.sh` → `nginx -t` → reload(HTTPS-nginx.md). 갱신 전에는 `/version.json`이 SPA의 `index.html`로 답해 배포 확인이 실패한다(16, 안전하지만 헷갈림)
5. `sha256sum /opt/homestamp/deploy/deploy-front.sh` → Terraform `deploy_front_script_sha256` → plan·apply(인프라 담당이 승인 뒤)
6. GitHub `FRONT_IMAGE_REPOSITORY` 변수(백엔드 `IMAGE_REPOSITORY`와 다름) → `deploy.yml`을 `component=front`로
- 첫 배포는 `current`가 없거나 손으로 둔 링크인 상태에서 시작한다. 확인에 실패하면 그 상태(없음·이전 링크)로 돌리고 그 상태를 확인한다(없음 = `version.json` 404)

## 백엔드와 함께 바뀔 때 (순서)

- API는 Expand–Contract. **백엔드 먼저**(필드 추가) → 확인 → **화면**(새 필드 사용) → 다음 배포에서 옛 필드 제거
- 화면만 되돌려도 백엔드는 그대로다(그 반대도). 옛 화면이 새 API와, 새 화면이 옛 API와 잠깐 같이 돌 수 있으므로 둘 다 한 판 앞뒤와 맞게 만든다
- 둘을 동시에 돌리지 않는다(잠금으로 3)

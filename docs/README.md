# homestamp 문서

세입자와 집주인이 집 상태·수리·퇴거 정산 기록을 함께 남기는 반응형 웹, homestamp(homestamp.cloud)의 기획·설계 문서예요. **여기가 원본**이고, 노션 등은 사본이에요.

## 읽는 순서

| 순서 | 문서 | 무엇을 |
|---|---|---|
| 1 | `planning/01-이야기로-보는-흐름.md` | 서윤(세입자)·정호(집주인) 이야기로 보는 전체 흐름 |
| 2 | `planning/GLOSSARY.md` | 용어. 화면·코드·문서는 이 말을 써요 |
| 3 | `planning/3-상태와-규칙.md` | 상태, 규칙, 보이는 범위, 불변식. **가장 먼저 맞아야 하는 문서** |
| 4 | `planning/2-사용자-시나리오.md` | 시나리오별 흐름 |
| 5 | `planning/10-화면-기본-틀.md` | 화면 틀과 버튼 문구 |
| 6 | `planning/7-요구사항-명세.md` | 요구사항, 수용 기준, API, 오류 코드 |
| 7 | `planning/6-ERD-초안.md` | 테이블과 불변식 대응 |
| 8 | `planning/4-인프라-아키텍처.md` | 인프라, 배포, 보안, CI |
| 9 | `planning/11-프로젝트-구조.md` | 패키지, 계층, 의존 방향, 이름 짓기 |
| 10 | `planning/8-WBS.md` | 일정과 나눈 일 |

- `submission/`: 제출용으로 줄인 판(시나리오, 상태와 규칙, 인프라, WBS). 내용이 다르면 `planning/`이 맞아요.
- `runbooks/`: 운영 절차(유출 대응).
- `decisions.md`: 결정 기록(유일). 왜 그렇게 정했는지는 여기서 찾아요.

## 문서끼리 다르면

`3-상태와-규칙.md` → `GLOSSARY.md` → `7-요구사항-명세.md` → `6-ERD-초안.md` → `10-화면-기본-틀.md` 순서로 앞의 것이 맞아요. 다른 곳을 발견하면 앞 문서에 맞춰 고치는 PR을 올려 주세요.

## 바꾸는 법

1. 규칙이 바뀌면 영향받는 문서를 모두 고쳐요(상태와 규칙 → 명세 → ERD → 화면 → 제출용).
2. `decisions.md` 맨 위에 한 줄(날짜, 무엇을, 왜, 고친 문서) 더해요.
3. 둘을 **한 PR**로 올려요. PR 제목은 `docs(docs): …`.

지켜야 할 것: 기록 수정·삭제 기능, 판정·법적 판단 문구, 주민등록번호 처리, 외부 CDN·외부 OCR, 비밀값 커밋은 넣지 않아요(`decisions.md` 원칙).

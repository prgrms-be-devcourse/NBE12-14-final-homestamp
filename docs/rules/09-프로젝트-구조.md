## 2. 백엔드 패키지

기준 패키지: `com.chilsuitjo.back`. **도메인별**로 나누고, 도메인 안을 여섯 폴더로 나눠요. 비어 있는 폴더는 만들지 않아요.

```
com.chilsuitjo.back
├── global/          공통: security, scheduler, error, response, common, config
├── member/  auth/  room/  inspection/          (A)
├── action/  repair/  correction/               (B)
├── proposal/  payment/  settlement/  photo/    (C)
├── notification/  link/                        (D)
└── respond/         확인 카드 보내기 조립      (D)
```

**한 도메인 안**

```
repair/
├── controller/     RepairController
├── dto/            요청·응답 DTO, 다른 도메인과 주고받는 값
├── service/        RepairService(입구), 이벤트 리스너
├── entity/         RepairCase, RepairContent (JPA 엔티티)
├── rule/           RepairTransitions(apply), 상태 값, enum, 도메인 이벤트
└── repository/     RepairCaseRepository, 외부 호출
```

| 폴더 | 들어가는 것 |
|---|---|
| `controller/` | 컨트롤러. 요청을 받아 `service/`를 부르고 `dto/`로 돌려준다 |
| `dto/` | 화면 요청·응답(`*Request`, `*Response`), 다른 도메인과 주고받는 값. 엔티티를 밖으로 내보내지 않으려고 둔다 |
| `service/` | 입구 서비스(`*Service`, 다른 도메인이 부르는 공개 메서드)와 이벤트 리스너 |
| `entity/` | JPA 엔티티. DB 테이블 모양 |
| `rule/` | 규칙(03 "상태와 규칙"을 옮긴 코드): 상태 전이(`*Transitions`, 순수 함수 `apply`), `apply`가 다루는 상태 값, enum, 도메인 이벤트. `apply`는 Repository·Clock·다른 서비스를 부르지 않는다(04 4-0). 업무 영역을 뜻하는 "도메인"(`repair` 등 패키지)과 헷갈리지 않게 `domain`이라 부르지 않는다 |
| `repository/` | `*Repository`(Spring Data)와 외부 호출(문자 업체, S3 등) |

| 주인 | 패키지 | 내용 |
|---|---|---|
| A | `member` `auth` `room` `inspection` | 회원, 로그인·토큰, 호실·당사자·부위·연결, 입주·퇴거 점검 |
| B | `action` `repair` `correction` | 행동 기록·해시 체인, 수리 건, 고치기 |
| C | `proposal` `payment` `settlement` `photo` | 돈 안건 장치, 지불, 정산·송금·보증금, 사진 |
| D | `notification` `link` `respond` | 응답 요청·기다림·통지·아웃박스, 링크, 확인 카드 |

## 3. 부르는 방향

**화살표는 위에서 아래로만** 가요. 같은 층끼리는 공개 서비스로만 부르고, 서로 부르지 않아요.

```
[맨 위]   respond
[도메인]  member · auth · room · inspection · repair · proposal · payment · settlement · photo · link
[아래층]  action · correction · notification
[바닥]    global
```

| 규칙 | 내용 |
|---|---|
| 도메인을 넘는 참조 | **ID 값만**(UUID). JPA 관계(`@ManyToOne` 등)는 같은 도메인 안에서만. DB 외래 키는 그대로 둬요 |
| 행동 기록 | 상태를 바꾸는 요청은 모든 도메인이 `ActionPipeline` 하나로 처리해요(아래 3-1). `action`은 어떤 도메인도 import하지 않아요 |
| 기다림·통지 | 도메인이 `notification`에 요청을 만들고, "혼자 진행할 수 있나"를 물어봐요. `notification`은 도메인을 부르지 않아요 |
| 고치기 | `correction`은 `Correctable` 인터페이스만 두고, 각 도메인이 구현해요 |
| 아래에서 위로 알릴 때 | **같은 트랜잭션 안의 동기 도메인 이벤트**. 예: 지불 금액이 확인돼 바뀜 → `PaymentAmountConfirmed` → `settlement`가 후보를 "다시 확인 대기"로 |
| 확인 카드 | `respond`는 도메인의 공개 서비스만 불러요. 어떤 도메인도 `respond`를 부르지 않아요 |
| 잠금 | 모든 행동은 맨 먼저 **호실 기록 행**을 잠가요(해시 체인 번호). 같은 호실의 행동은 한 줄로 서서 이벤트가 끼어도 교착이 없어요 |

**같은 도메인 층끼리 방향 (초안, 1일차 확정)**

| 부르는 쪽 → 불리는 쪽 | 이유 |
|---|---|
| `repair` → `proposal` | 수리비 나누기 안건 |
| `settlement` → `proposal` | 정산 항목·보증금 안건 |
| `settlement` → `repair`, `payment` | 후보 계산(읽기) |
| `repair`, `inspection`, `payment`, `settlement` → `photo` | 사진 붙이기 |
| `room` ← 모두 | 호실·당사자·권한 확인(`RoomAccessService.require(호실 기록 ID, 회원 ID)` → `RoomAccess`, 당사자가 아니면 `NOT_FOUND`) |
| `link` → `repair`, `inspection` | 링크로 보여 줄 기록 읽기 |

### 3-1. 상태를 바꾸는 요청: `ActionPipeline`

상태를 바꾸는 요청(06 4-0 "상태를 바꾸는 요청")은 모두 `action`의 `ActionPipeline`을 지나요. 각 도메인은 **상태 값·전이·저장** 세 가지만 만들고, 잠금·멱등·호실 단위 거절·행동 기록 순서는 pipeline이 지켜요(`decisions.md` 2026-11-16·17).

```java
// action/service
public interface ActionPipeline {
  /** 행동 하나. executeAll의 바로가기. */
  <S> ActionResult<S> execute(UUID roomRecordId, UUID memberId, String idempotencyKey, ActionCommand<S> command);

  /** 한 요청의 여러 행동(예: 초대 SHARE_CONSENT + INVITE). 한 트랜잭션·한 호실, 키는 <키>, <키>#2 … */
  List<ActionResult<?>> executeAll(UUID roomRecordId, UUID memberId, String idempotencyKey, List<ActionCommand<?>> commands);
}

// action/rule: action이 두고 room이 구현한다(room → action 방향, 위 표 "고치기"의 Correctable과 같은 방식)
public interface RoomGateReader {
  /** 호실 기록 행을 잠그고(FOR UPDATE) 잠근 뒤의 최신 상태로 RoomGate를 만든다. 당사자가 아니면 NOT_FOUND. */
  RoomGate lockAndRead(UUID roomRecordId, UUID memberId);
}
```

**계약**: 호실 단위 거절(아래 3단계)은 **잠금을 얻은 뒤 읽은 최신 상태**로만 판단한다. 도메인이 잠금 전에 읽은 값(`RoomAccess` 등)을 pipeline에 넘기지 않는다. 잠금을 기다리는 동안 정산 완료·공유 중단이 끼어들 수 있기 때문이다.

| 타입 | 위치 | 만드는 쪽 | 내용 |
|---|---|---|---|
| `RoomGate` | `action/dto` | `RoomGateReader`(room 구현) | `roomRecordId`, `memberId`, `side`(`PartySide`), `settled`(정산 완료), `joinedAway`(합류 전 기록), `mySharingStopped`(내가 공유를 그만둠). `action`이 `room`을 import할 수 없어서 따로 둔다. 도메인은 만들지 않고, pipeline이 1단계에서 받는다 |
| `RoomGateReader` | `action/rule`(인터페이스) | `room`이 구현(`room/service/`) | `RoomGate lockAndRead(roomRecordId, memberId)`. 호실 기록 행 잠금과 room 상태 → `RoomGate` 변환을 room 한 곳에서 한다 |
| `ActionCommand<S>` | `action/dto` | 부르는 도메인 | `type`(`ActionType`), `target`(`ActionTarget`), `store`(`StateStore<S>`), `transitions`(`Transitions<S>`), `input`(apply에 넘길 값), `reason`, `seenVersionNo`(06 `seenVersionNo`) |
| `ActionTarget` | `action/dto` | 부르는 도메인 | 05 `action`의 대상 칸 중 하나(종류 + ID). 없으면 호실 기록 자체 |
| `ActionResult<S>` | `action/dto` | pipeline | `actionId`, `state`(저장한 뒤 상태), `replayed`(같은 키로 다시 온 요청이면 true, 06 4-0 `Idempotent-Replayed`) |
| `ActionContext` | `action/dto` | pipeline | apply에 넘기는 행동 정보: 주체 측·회원 ID, 서버 시각, `type`, `reason`, `seenVersionNo`. `apply`는 `Clock`을 부르지 않아서(2장 `rule/`) 시각을 여기로 받는다 |
| `ActionType` | `action/rule` | B | 05 2-2 행동 종류(`RESPOND_DEFECT` 등). 행동마다 응답류인지(`responseKind`), 정산 뒤에 되는지(`allowedAfterSettled`)를 표시한다 |
| `StateStore<S>` | `action/rule`(인터페이스) | 각 도메인 `XxxStateStore`(`service/`) | `S loadForUpdate(ActionTarget)`, `void save(S before, S after)`. Repository로 엔티티와 상태 값을 오간다. 링크·응답 요청·문자는 pipeline 단계가 아니라 이 `save`(원인 행동의 저장)에서 부른다 |
| `Transitions<S>` | `action/rule`(인터페이스) | 각 도메인 `XxxTransitions`(`rule/`) | `S apply(S current, ActionContext context, Object input)`. 순수 함수, 안 되면 `BusinessException`. 기록 단위 규칙만 보고 호실 단위 규칙은 보지 않는다 |
| `XxxState` | 각 도메인 `rule/` | 각 도메인 | `apply`가 다루는 상태 값(2장 `rule/`) |

**pipeline이 지키는 순서** (여러 행동이면 1~3은 한 번, 4~7은 행동마다. 하나라도 실패하면 모두 되돌림)

1. `roomGateReader.lockAndRead`로 호실 기록 행을 잠그고(위 "잠금") 잠근 뒤의 `RoomGate`를 읽는다
2. 멱등: 같은 (주체, 키)가 이미 있으면 새로 만들지 않고 지금 상태와 `replayed = true`를 돌려준다. 같은 키에 다른 대상·다른 행동이면 `IDEMPOTENCY_KEY_REUSED`(06 4-0)
3. 호실 단위 거절: `settled`이고 `allowedAfterSettled`가 아니면 `SETTLED`, `mySharingStopped`이고 응답류면 `SHARING_STOPPED`, `joinedAway`면 새 행동을 받지 않음(06 ROOM-6, 예외: 사진 지우기 PHO-5c. 오류 코드는 06 4-10에 아직 없어 구현 PR에서 정함)
4. `store.loadForUpdate(target)`
5. `transitions.apply(지금 상태, context, input)`
6. `store.save(before, after)`
7. 행동 기록 저장(`room_seq`·`prev_hash`·`hash`, 05 `action`)

**도메인에서 쓰는 모양**

```java
// 호실 단위 거절은 pipeline이 잠금 뒤에 판단하므로 도메인은 RoomGate를 만들지 않는다.
// 조회 화면처럼 잠금 없이 당사자만 확인할 때는 roomAccessService.require(...)를 따로 쓴다.
ActionResult<RepairState> result = actionPipeline.execute(roomRecordId, memberId, idempotencyKey,
    new ActionCommand<>(ActionType.RESPOND_DEFECT, ActionTarget.repairCase(repairCaseId),
        repairStateStore, repairTransitions, request, request.reason(), request.seenVersionNo()));
```

**가짜(1주차 2일차)**: `FakeActionPipeline`은 DB·해시 없이 메모리로 1~6을 실제와 같은 순서로 하고, 남긴 행동 목록을 돌려준다. 1단계는 `FakeRoomGateReader`에 적어 둔 `RoomGate`를 읽는다(테스트가 호실 상태를 직접 정함). 다른 도메인은 이 가짜로 서비스·테스트를 먼저 짜고, 실제 구현이 들어와도 인터페이스는 그대로다.

## 2. 백엔드 패키지

기준 패키지: `com.chilsuitjo.back`. **도메인별**로 나누고, 도메인 안을 여섯 폴더로 나눠요. 비어 있는 폴더는 만들지 않아요.

```
com.chilsuitjo.back
├── global/          공통: security, scheduler, error, response, common, config
├── member/  auth/  room/  inspection/          (A)
├── action/  repair/  correction/               (B)
├── proposal/  payment/  settlement/  photo/    (C)
├── notification/  link/                        (D)
└── respond/         확인 카드 보내기·홈 조립   (D)
```

**한 도메인 안**

```
repair/
├── controller/     RepairController
├── dto/            요청·응답 DTO, 다른 도메인과 주고받는 값
├── service/        RepairService(입구), 이벤트 리스너
├── entity/         RepairCase, RepairContent (JPA 엔티티)
├── rule/           RepairTransitions(apply), 상태 값, enum, 도메인 이벤트
└── repository/     RepairCaseRepository, 외부 호출
```

| 폴더 | 들어가는 것 |
|---|---|
| `controller/` | 컨트롤러. 요청을 받아 `service/`를 부르고 `dto/`로 돌려준다 |
| `dto/` | 화면 요청·응답(`*Request`, `*Response`), 다른 도메인과 주고받는 값. 엔티티를 밖으로 내보내지 않으려고 둔다 |
| `service/` | 입구 서비스(`*Service`, 다른 도메인이 부르는 공개 메서드)와 이벤트 리스너 |
| `entity/` | JPA 엔티티. DB 테이블 모양. 롬복은 클래스에 `@Getter`와 `@NoArgsConstructor(access = AccessLevel.PROTECTED)`만 쓴다(아래 "롬복") |
| `rule/` | 규칙(03 "상태와 규칙"을 옮긴 코드): 상태 전이(`*Transitions`, 순수 함수 `apply`), `apply`가 다루는 상태 값, enum, 도메인 이벤트. `apply`는 Repository·Clock·다른 서비스를 부르지 않는다(04 4-0). 업무 영역을 뜻하는 "도메인"(`repair` 등 패키지)과 헷갈리지 않게 `domain`이라 부르지 않는다 |
| `repository/` | `*Repository`(Spring Data), `*StateStore`(3-1 `StateStore` 구현), 외부 호출(문자 업체, S3 등) |

**롬복**: 쓰는 것은 `@Getter`, `@NoArgsConstructor(access = AccessLevel.PROTECTED)`(JPA 빈 생성자), `@RequiredArgsConstructor`(서비스 생성자 주입)뿐이다. `@Setter`·`@Data`·`@EqualsAndHashCode`·`@ToString`·`@Builder`·`@AllArgsConstructor`·`@With`·`@Value`·`@SneakyThrows`·`lombok.experimental.*`·롬복 `val`/`var`·로그(`@Slf4j` 등)·`@NonNull`·`@Synchronized`·`@Cleanup`·`@Locked`·`@Jacksonized`·`@Getter(lazy = true)`·`onX`는 `back/lombok.config`가 컴파일 오류로 막는다(고칠 수 없는 행에 setter가 열리고, 엔티티의 equals·toString은 지연 로딩·순환 참조를 건드리고, 빌더·전체 인자 생성자는 생성자의 검사를 건너뛰고, `@With`는 고칠 수 없는 행을 바꾼 복사본을 만든다). 자바 `var` 키워드는 쓸 수 있다. `@NoArgsConstructor`를 `PROTECTED` 없이(public으로) 쓰는 것과 같은 접근 수준은 설정으로 막을 수 없어서 리뷰로 본다. getter를 내보내면 안 되는 칸(예: `RepairContent`의 `newRow`)은 그 필드에 `@Getter(AccessLevel.NONE)`를 붙인다. 값 객체·DTO는 record를 쓴다. `byte[]` 칸(해시·지문)은 `@Getter`가 내부 배열을 그대로 내보내므로 손으로 쓴 getter로 복사본을 돌려준다(롬복은 이미 있는 메서드를 만들지 않는다). 검사·복사가 있는 생성자와 로직 메서드는 그대로 손으로 쓴다.

| 주인 | 패키지 | 내용 |
|---|---|---|
| A | `member` `auth` `room` `inspection` | 회원, 로그인·토큰, 호실·당사자·부위·연결, 입주·퇴거 점검 |
| B | `action` `repair` `correction` | 행동 기록·해시 체인, 수리 건, 고치기 |
| C | `proposal` `payment` `settlement` `photo` | 돈 안건 장치, 지불, 정산·송금·보증금, 사진 |
| D | `notification` `link` `respond` | 응답 요청·기다림·통지·아웃박스, 링크, 확인 카드, 홈(06 4-2 `GET /api/me/home`) |
| 공통 | `global` | 보안, 예약 작업 틀, 오류 응답, 설정. 두 도메인 이상이 같은 뜻으로 쓰는 enum·요청 DTO는 `global/common`(`PartySide`, `Answer`, `AckState`, `ClosedReason`, `TargetKind`(기록 대상 종류, `action`·`notification`이 같이 씀), `common/dto`의 `RespondRequest`·`ReasonRequest`·`AnswerResult`(응답하기 결과)·`SupplementRequest`(보충 요청)), 응답 모양은 `global/response`(`CreatedResponse`, `CursorPage`). 모두가 쓰는 바닥 층이고, 주로 맡는 사람은 `global/security`는 A, `global/scheduler`는 D(07 0장) |

## 3. 부르는 방향

**화살표는 위에서 아래로만** 가요. 같은 층끼리는 공개 서비스로만 부르고, 서로 부르지 않아요. 예외는 아래 표 "아래층끼리"에 적은 방향뿐이에요.

```
[맨 위]   respond
[도메인]  member · auth · room · inspection · repair · proposal · payment · settlement · photo · link
[아래층]  action · correction · notification
[바닥]    global
```

| 규칙 | 내용 |
|---|---|
| 도메인을 넘는 참조 | **ID 값만**(UUID). JPA 관계(`@ManyToOne` 등)는 같은 도메인 안에서만. DB 외래 키는 그대로 둬요 |
| 행동 기록 | 상태를 바꾸는 요청은 모든 도메인이 `ActionPipeline` 하나로 처리해요(아래 3-1). `action`은 어떤 도메인도 import하지 않아요 |
| 기다림·통지 | 도메인이 `notification`에 요청을 만들고, "혼자 진행할 수 있나"를 물어봐요. `notification`은 도메인을 부르지 않아요. 상대의 연결 상태·문자 설정은 부르는 쪽이 넘기지 않고, `notification`이 두는 포트(가칭 `CounterpartReader`)를 `room`이 구현해 읽어요. 정산·수리의 `StateStore`(`load`·`save`)도 자리 상태(공유 중단·탈퇴, 공유 중단 시각)를 room 메서드를 따로 두지 않고 이 포트로 읽어요(내 측·상대 측 둘 다. 포트 모양은 D가 정함). 인증 문자는 요청·아웃박스를 거치지 않고 `auth`가 인증 행을 커밋한 뒤 `notification`의 바로 보내기를 불러요(04 4-2). 요청은 **대상 + 요청 종류**로 다뤄요(점검 확인만 요청한 측까지): 답이 저장되면 `WaitService.answered(대상, 종류, 답한 측)`(열린 요청만 닫고 닫힌 요청은 다시 열지 않아요), 보충·다시 요청과 제안 바꾸기는 `restart`(호실·요청한 측을 함께 받고, 새로 열지·묶을지·기한은 notification이 종류를 보고 정해요), 제안의 역제안은 `answered` 다음 `open`(05 `proposal` ③), 지금 단계에서 열 수 있는지는 `canOpen`. 자세한 규칙은 `WaitService` Javadoc이 원본이에요. 자리 상태는 `CounterpartReader.read(호실, 내 측)` → `RoomParties`(호실 단계와 두 자리. 공유 중단 제한 판단은 `RoomParties`에, 상대 탈퇴가 앞서요. 단계별로 열 수 있는 요청은 `RequestOpening`) |
| 아래층끼리 | `notification → action`(서버 행동 `RENOTIFY`·`MARK_UNCONFIRMED`·`MARK_UNDELIVERED`를 pipeline으로 남김), `correction → action`(고친 내용 행동), `correction → notification`(고친 내용 확인 요청)만 허용해요. 반대 방향은 없어요(`action`은 둘 다 모르고 `notification`은 `correction`을 모름. 고리는 아래 ArchUnit이 막음) |
| 응답 공통 처리 | 맞아요·보류·이견, 다시 요청 7일·근거 필수, 맞아요는 되돌릴 수 없음을 `action/rule`의 `AnswerSupport` 한 곳에서 처리해요(순수 함수: `answer`·`canAnswer`·`rerequest`·`canRerequest`·`nextRerequestAt`, [상황이 바뀌었어요]용 `requireEvidence`·`checkInterval`). 입력은 `Answerable`(기록한 측·응답 값·판 번호·마지막 다시 요청 시각), payload는 `AnswerPayload`(답만, 사유는 행동 기록의 `reason`). 보충 설명은 `action`의 `SupplementWriter`로 `record.supplement`에 남겨요(수리 건 하자·지불·점검 항목 공통). 수리·점검·지불·송금·고친 내용·원인 설명(응답만)이 각자 `apply`에서 불러요. 볼 수 없는 기록·그 단계에서 할 수 없는 행동(거주 종료 뒤 열린 수리 건의 종료 확인 등)은 도메인이 먼저 막아요. 거주 종료 뒤 다시 요청은 `canOpenRequest`로 막혀요. 쓰는 법은 `docs/guides/action-pipeline.md` 8장. 확인 카드(`respond`)와 이름을 나눠요 |
| 고치기 | `correction`은 `Correctable` 인터페이스만 두고, 각 도메인이 구현해요(`load`·`applyNow`·`mergeConfirmed`·`digestOf`·`attachEvidence`). 거절된 고친 내용을 다시 보낼 때 더한 근거 사진은 `correction`이 `photo`를 부르지 않고, 대상 도메인이 `attachEvidence`에서 `PhotoService.attach`로 붙여요(05 `photo.correction_request_id`) |
| 아래에서 위로 알릴 때 | **같은 트랜잭션 안의 동기 도메인 이벤트**. 예: 지불의 같이 확인한 판이 바뀜(ACK, 고친 내용 확인. 금액만이 아니라 어느 칸이든) → `PaymentAmountConfirmed` → `repair`가 `confirmedTotal`로 `rebase`, `settlement`가 후보를 다시 계산해 지금 항목과 다를 때만 "다시 확인 대기"로(decisions 2026-11-24) |
| 확인 카드 | `respond`는 도메인의 공개 서비스만 불러요. 어떤 도메인도 `respond`를 부르지 않아요 |
| 잠금 | 모든 행동은 맨 먼저 **호실 기록 행**을 잠가요(해시 체인 번호). 같은 호실의 행동은 한 줄로 서서 이벤트가 끼어도 교착이 없어요 |

### 3-1. 상태를 바꾸는 요청: `ActionPipeline`

**행동 기록을 남기는 요청**(06 4-0 "상태를 바꾸는 요청"에서 `Idempotency-Key`가 필수인 요청)은 모두 `action`의 `ActionPipeline`을 지나요. 06 4-0이 행동 기록에서 뺀 요청(로그인, 인증 문자, 업로드 표, 사진 주소, 알림 읽음)과 회원 신원 칸 바꾸기(05 0장 신원 예외)는 pipeline을 쓰지 않아요. 각 도메인은 **상태 값·전이·저장** 세 가지만 만들고, 잠금·멱등·호실 단위 거절·행동 기록 순서는 pipeline이 지켜요(`decisions.md` 2026-11-16·17·18·19).

```java
// action/service/ActionPipeline.java (구현이 하나라 클래스)
@Service
public class ActionPipeline {
  // 트랜잭션은 pipeline이 연다(아래 "트랜잭션 경계"). 부르는 쪽은 @Transactional을 두지 않는다
  public BatchResult executeAll(ActionBatch batch); // 입구 하나

  public <S> PipelineResult<S> execute(ActionCommand command, StateStore<S> store, Transitions<S> rules);
  // = executeAll(ActionBatch.single(command, store, rules)). 행동 하나짜리 바로가기

  public <S> PipelineResult<S> create(ActionCommand command, StateStore<S> store, Transitions<S> rules);
  // 새 기록을 만드는 행동 하나짜리(REGISTER 등). command.target()은 비우고, save가 만든 기록이 결과의 대상이 된다
}

// action/dto/ActionBatch.java (한 요청 · 한 호실의 행동 목록)
public final class ActionBatch {
  // 키가 비었거나 #가 들었거나 64자(MAX_KEY_LENGTH)를 넘으면 400 VALIDATION_FAILED. 서버·링크 주체가 만드는 키(link-view:<UUID>:… 등)도 같다
  public static ActionBatch of(UUID roomRecordId, Actor actor, String idempotencyKey);
  // 호실을 만드는 요청(CREATE_ROOM)만. 아직 호실 행이 없어 잠금·공통 거절을 건너뛴다(아래 순서 1·3)
  public static ActionBatch newRoom(Actor actor, String idempotencyKey);
  public static <S> ActionBatch single(ActionCommand command, StateStore<S> store, Transitions<S> rules);

  // 상태 있는 행동. 대상은 앞 단계 결과로 정할 수 있다(호실 자체면 done -> null)
  public <S> ActionBatch step(ActionType type, Function<List<ActionResult>, ActionTarget> target,
                              StateStore<S> store, Transitions<S> rules);
  // 새 기록을 만드는 행동(REGISTER 등). 물을 대상이 없고 save가 만든 기록을 돌려준다
  public <S> ActionBatch creating(ActionType type, StateStore<S> store, Transitions<S> rules);
  public <S> ActionBatch step(ActionStep<S> step); // seenVersionNo·content·reason·payload까지 줄 때

  // 상태 칸이 없는 행동(SHARE_CONSENT 등). 행동 기록만 남긴다
  public ActionBatch record(ActionType type, Map<String, Object> payload);
  public ActionBatch record(ActionType type, Function<List<ActionResult>, ActionTarget> target, Map<String, Object> payload); // 대상이 있는 기록만(LINK_VIEW 등)
}

// action/service/StateStore.java ← 각 도메인이 구현
public interface StateStore<S> {
  S load(ActionCommand command);                  // 새로 만드는 행동이면 빈 상태
  SavedState save(ActionCommand command, S next); // 새로 만든 대상·판이 있으면 알려 준다
}

// action/rule/Transitions.java ← 각 도메인이 구현
public interface Transitions<S> {
  S initial();
  S apply(S now, ActionEntry action); // 위반이면 BusinessException → 저장·기록 없음
}

// action/rule/RoomGateReader.java ← room이 구현(room → action 방향, 위 표 "고치기"의 Correctable과 같은 방식)
public interface RoomGateReader {
  /** 호실 기록 행을 잠그고(FOR UPDATE) 잠근 뒤의 최신 상태로 RoomGate를 만든다. */
  RoomGate lockAndRead(UUID roomRecordId, Actor actor);
  /** 잠그지 않고 같은 값을 읽는다. 상세 조회의 availableActions에만 쓴다. */
  RoomGate read(UUID roomRecordId, Actor actor);
}
```

**계약**: 호실 단위 거절(아래 3단계)은 **잠금을 얻은 뒤 읽은 최신 상태**로만 판단한다. 도메인이 잠금 전에 읽은 값(`RoomAccess` 등)을 pipeline에 넘기지 않는다. 잠금을 기다리는 동안 정산 완료·공유 중단이 끼어들 수 있기 때문이다. pipeline의 거절은 "막는 조건 하나에 오류 하나"이고 행동은 표시로 막을지 말지만 정한다(아래 순서 3). 같은 조건이라도 행동마다 결과가 다른 판단(예: 상대가 공유를 그만둔 동안 정산 끝내기는 `finish`면 `INVALID_STATE`, `finish/alone`이면 `SOLO_NOT_ALLOWED`, 06 CONS-3g)은 pipeline이 아니라 그 도메인의 `Transitions`가 본다. `StateStore.load`는 잠금 뒤에 불리므로(아래 순서 5) 그때 읽은 상대 상태도 최신이다. 상대가 탈퇴했으면(상대 자리 상태가 `WITHDRAWN`) 상대 공유 중단에 따른 제한은 하지 않고, 남아 있는 상대의 `sharing_stopped_at`은 보지 않는다(03 B, 06 CONS-3q). 상대 탈퇴는 상대 공유 중단보다 앞서며, `RoomGate.mySharingStopped`도 같은 기준이다(06 CONS-3p).

**pipeline이 지키는 순서** (1·2는 요청마다 한 번, 3~9는 단계마다. 어느 단계든 예외면 저장도 기록도 모두 되돌림)

1. `roomGateReader.lockAndRead`로 호실 기록 행을 잠그고(위 "잠금") 잠근 뒤의 `RoomGate`를 읽는다. `newRoom`이면 건너뛴다(아직 아무도 그 호실을 모름)
2. 멱등: (주체, `<키>`)인 행동이 이미 있으면 그 행동의 `request_id`로 그 요청의 행동 전부를 모아 `replayed = true`로 돌려주고 끝낸다. 처음 요청과 다르면 `IDEMPOTENCY_KEY_REUSED`(06 4-0). 같은 요청이란: 같은 호실이고, 요청 주체가 남긴 행동(`<키>`, `<키>#n`)이 이번 단계들과 **순서대로** 짝이 맞는 것이다. `when`이 있는 단계는 짝이 없어도 되고, 짝이 맞은 단계는 대상도 같아야 한다(새로 만드는 단계는 종류만 보고 부모 ID 같은 payload 값은 비교하지 않음, 대상을 다시 정하다 실패하면 다른 요청). 딸린 행동은 비교하지 않는다. 한계: 처음에 건너뛴 단계는 기록이 없어 조건부 단계만큼 구성이 다른 요청은 가리지 못하고, 새로 만드는 단계는 같은 호실의 다른 부모(지불의 수리 건 등)에 쓴 같은 키도 처음 결과로 돌려준다(앞의 것은 단계를 서버 코드가 버튼마다 정하므로 다른 버튼이 같은 키를 쓴 화면 버그에서만, 뒤의 것은 화면이 다른 요청에 키를 다시 쓴 버그에서만 생기고, 돌려주는 결과는 저장된 행동과 같다)
3. 호실 단위 거절(`server`·`ops`와 `newRoom`은 건너뜀). 겹치면 앞의 것을 돌려준다. 순서의 기준은 06 4-10이고, 여기에는 각 조건을 푸는 표시만 더해 적는다: 정산 완료이고 `AFTER_SETTLED`가 아니면 `SETTLED` → 거주 종료이고 `blockedAfterEnded`면 `ROOM_ENDED` → 합류 전 기록이고 `ON_JOINED`가 아니면 `JOINED_RECORD` → 내가 공유를 그만뒀고 `WHILE_SHARING_STOPPED`가 아니면 `SHARING_STOPPED`. 정산 완료·거주 종료는 공유 중단 중에도 양쪽에 보이는 사실이라(03 불변식 18 예외) 먼저 돌려줘도 숨긴 기록이 드러나지 않는다. 링크 주체는 호실 상태를 알면 안 되므로(06 LINK-2), 링크 열람(`links/view`)은 호실이 정산 완료·합류 전 기록이면 link가 **pipeline을 부르기 전에** `LINK_INVALID`로 돌려주고 열람 기록(`LINK_VIEW`)은 남기지 않는다(#83). `LINK_VIEW`에는 허용 표시를 달지 않아서, 그래도 pipeline까지 오면 호실 단위 거절로 막혀 기록이 남지 않는다
4. 대상 정하기: `step`의 `target(앞 단계 결과)`. 다른 호실을 가리키면 거절
5. `store.load(command)`
6. `rules.apply(지금 상태, entry)`
7. `store.save(command, next)` → `SavedState`
8. 행동 기록: 키 `<키>`, `<키>#2` …, `room_seq` + 1, `prev_hash` = 앞 행동의 `hash`(05 `action`). 한 요청의 모든 행동(딸린 행동 포함)에 pipeline이 요청마다 만든 `request_id`(UUID v7)를 같이 넣는다. `newRoom`이면 첫 행동이 `room_seq` 1이고 `prev_hash`는 시작값이다. 한 요청의 행동(딸린 행동 포함)은 pipeline이 요청마다 한 번 정한 같은 서버 시각(마이크로초로 자름)을 `apply`와 기록(`created_at`·해시 입력)에 함께 쓴다(#72)
9. 딸린 행동: 이 단계에서 `ActionFollowUps.add`로 쌓인 행동을 같은 방식으로 이어서 기록한다(주체는 `add`에 준 것, 키는 `<request_id>#n`. 주체가 `server`여도 요청마다 키가 달라 두 회원이 같은 키를 써도 부딪히지 않는다)

5단계 뒤 그 단계의 `when`이 거짓이면 6~9를 건너뛰고 다음 단계로 간다(기록도 남지 않음). 조건은 잠금 안에서 읽은 상태로 판단하므로 두 요청이 동시에 와도 한 번만 실행된다.

**pipeline에 넣지 않는 것**: 특정 행동·도메인을 위한 분기(`if (type == …)`). 조건은 부르는 쪽이 `when`으로 넘기고, 도중에 생기는 일은 `ActionFollowUps`로 남긴다. 그래서 조건이 늘어도 pipeline 코드는 그대로다.

**트랜잭션 경계**: pipeline이 맡는다. `executeAll`·`execute`가 트랜잭션을 열고 닫으며, 도메인 서비스는 pipeline 바깥에 `@Transactional`을 두지 않는다(바깥 트랜잭션이 있으면 아래 다시 찾기를 할 수 없음). 같은 키가 동시에 와 `UNIQUE(actor_key, idempotency_key)`에 걸리면 pipeline이 그 트랜잭션을 되돌린 뒤 **새 트랜잭션에서** 호실을 먼저 잠근 뒤(순서 1과 같음, 호실을 만드는 요청은 빼고) (주체, 키)로 처음 결과를 찾아 `replayed = true`로 돌려준다(06 4-0 "동시에 온 같은 키"). 다시 읽는 `load`도 잠금 뒤에 돈다. 조회만 하는 서비스는 pipeline과 상관없이 읽기 트랜잭션을 써도 된다.

**묶는 범위**: 한 요청 · 한 호실 · 행동만. 다른 호실의 행동, 서로 다른 요청, 작업자의 여러 호실은 묶지 않고 각각 `executeAll` 한 번씩이다(작업자는 호실마다 트랜잭션, 05 2-3).

**도메인에서 쓰는 모양**

```java
// 새 기록을 만드는 행동 하나: 하자 등록(RepairService). 결과의 대상이 새 수리 건이다
PipelineResult<RepairState> registered = pipeline.create(
    new ActionCommand(roomRecordId, Actor.member(memberId), ActionType.REGISTER, idempotencyKey,
        null, null, content, null, Map.of()),
    repairStateStore, repairTransitions);

// 행동 하나: 하자 응답(RepairService)
pipeline.execute(
    new ActionCommand(roomRecordId, Actor.member(memberId), ActionType.RESPOND_DEFECT, idempotencyKey,
        ActionTarget.repairCase(repairCaseId), req.seenVersionNo(), content, req.reason(),
        Map.of("answer", req.answer())),
    repairStateStore, repairTransitions);

// 여러 행동: 처음 초대 [동의하고 보여 주기](A의 초대 서비스)
pipeline.executeAll(ActionBatch.of(roomRecordId, Actor.member(memberId), idempotencyKey)
    .record(ActionType.SHARE_CONSENT, Map.of("consentVersion", req.consentVersion()))
    .step(ActionType.INVITE, done -> ActionTarget.party(partyId), partyStateStore, partyTransitions));

// 호실 만들기(A의 호실 서비스): 아직 호실 행이 없어 newRoom. save가 새 호실을 SavedState.target으로 돌려준다
// RoomGate를 읽지 않으므로 회원의 측은 부르는 쪽이 넣는다
BatchResult created = pipeline.executeAll(ActionBatch.newRoom(Actor.member(memberId).withSide(side), idempotencyKey)
    .step(ActionType.CREATE_ROOM, done -> null, roomStateStore, roomTransitions));
UUID roomRecordId = created.first().target().id(); // 다시 온 요청이면 처음 만든 호실 ID
```

내 도메인에서 따라 만드는 순서(상태 값·규칙·저장·서비스·컨트롤러), 메서드 고르기, 테스트 준비물(`ActionPipelineFixture`), 자주 하는 실수는 `docs/guides/action-pipeline.md`에 있다.

호실 단위 거절은 pipeline이 잠금 뒤에 판단하므로 도메인은 `RoomGate`를 만들지 않는다. 조회 화면처럼 잠금 없이 당사자만 확인할 때는 `roomAccessService.require(...)`를 따로 쓴다.

**가짜(1주차 2일차)와 진짜**: pipeline은 처음부터 진짜이고, 안쪽 부품 중 잠금(`RoomGateReader`)만 가짜였다. 지금은 room의 `JpaRoomGateReader`가 1단계를 맡아 `room_record`를 `FOR UPDATE`로 잠그고 `party`로 당사자를 확인한다(ROOM-2, #143). `FakeRoomGateReader`(테스트가 `RoomGate`를 직접 정함)는 테스트 코드로 옮겨 DB 없는 테스트(`ActionPipelineFixture`)만 `new`로 만들어 쓴다(빈이 아님, #140). 행동 기록 저장은 진짜(`JpaActionWriter`, `record.action`에 저장·해시 체인)이고, 메모리 가짜(`FakeActionWriter`)는 테스트 코드로 옮겨 DB 없는 테스트(`ActionPipelineFixture`)에서만 쓴다. 그래서 다른 도메인의 테스트도 실제와 같은 순서를 지난다. V1 뒤 부품이 진짜로 바뀌어도 각 도메인 코드는 바뀌지 않는다. 행동 기록 저장(`ActionWriter`)과 잠금은 pipeline 안쪽 부품이라 package-private이고, 다른 도메인이 직접 부를 수 없다. 그래서 `JpaActionWriter`는 2장의 `repository/`가 아니라 `action/service`에 두고 `@Repository`를 붙인다(중복 키가 Spring `DataIntegrityViolationException`으로 나와야 pipeline이 같은 키를 다시 찾을 수 있음). 읽기(`ActionReader`)도 트랜잭션 안에서만 부른다(`MANDATORY`).
